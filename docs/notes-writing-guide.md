# Notes 写作与图文标准

适用于本站后续新增或修改的 Notes，包括 Workbench 系列。以前三章的叙事方式、当前中性灰图集和现有 Markdown 组件为基准。具体篇章可以调整结构，不强制相同节数、图数或段落模板。

首次整理：2026-10-30。正文标准在本文维护；配色、画布和图表生成细节以 [Workbench 图表规范](diagrams/workbench/README.md)及 [style.json](diagrams/workbench/style.json)为准。双语与 CMS 行为见 [Notes 双语展示](experience-notes-i18n.md)，渲染行为见 [Markdown 呈现](experience-notes-markdown-ui.md)。

## 1. 写作前先确定本篇解决什么问题

先读相邻章节和目标位置的现有内容。对 AI 开发系列，至少对照：

- [第一章：基建与环境](notes/environment-infrastructure.zh.md)：先解释模型、Agent、工具与规约的职责，再进入配置与使用。
- [第二章：需求与产品定义](notes/scope-product-definition.zh.md)：承接上文，按不同起点推进到产品范围与验收，提示词放在实际使用位置。
- [第三章：架构与契约](notes/architecture-contracts.zh.md)：从约束到候选、职责、契约、失败与交接，给出判断依据和取舍。

开写前用几句话记录：读者已经知道什么、现在卡在哪里、本篇需要帮助读者做什么决定、读完应留下什么成果。先列叙事顺序与一个可贯穿的案例，再研究资料、安排图表和撰写正文。

对帮助入门者建立认识的文章，先给能力地图或问题全景，再逐步展开。读者需要先知道“有哪些方面值得考虑、什么时候需要”，然后才有能力选择实现方案。不要用面试考点、架构术语或工程检查表代替概念建立。

一个主题可以沿“用户遇到的问题 → 相关概念的通俗解释 → 同一案例怎样升级 → 可观察的验收结果”推进。先出现问题，再介绍消息队列、异步、幂等等名称；解释概念之间的关系，不能只在一张图里罗列缩写。概念地图用来展示全貌，正文用来讲清因果。

根据读者层级分配细节：入门正文保留判断与行动所必需的内容，具体参数、复杂异常、协议与框架深入实现移入进阶资料。每新增细节，检查它是否帮助当前读者作决定。覆盖完整意味着不遗漏主要问题，不能靠不断加小节、加表格实现。建立地图后，各分支仍应适度展开概念之间如何配合、一个具体流程怎样运行、失败后怎样处理及怎样验证；通俗表达也要保留足够的解释深度。

## 2. 按问题推进，同时让读者能够扫读

开篇简短承接上一阶段，说明当前问题与阅读目标。章节按读者的理解和决策过程组织；每节承担一个主要问题，解释需要、做法、边界与验收。

**叙事连贯，不等于连续写大段正文。** 先分配信息的呈现形式，再写具体句子：

- **短段落讲因果：** 一个段落只解释一个判断，通常 1–3 句。中文超过约 120 字时，优先检查能否拆分；不要连续堆放多段长解释。
- **分点讲并列项：** 条件、注意事项和验收用列表，每组通常 3–5 项；有先后顺序用编号。每项用简短的加粗词组提示主题，再解释动作与结果。
- **表格讲对应关系：** 概念与职责、故障与应对、指标与动作采用 2–3 列对照。单元格只留核心信息，不把长段落搬进表格。
- **图讲协作和流程：** 连接、分支、状态和执行次序优先用图；正文补充图中省略的规则。不要给所有内容加框，也不用图片替代可选择文字。
- **加粗帮助定位：** 标出结论、关键区别与操作对象，不整段加粗。小组标题可用独立加粗行，不为排版密度大量增加目录层级。

**完稿做一次扫读检查：** 只看标题、加粗句、表头和步骤，能否知道这一节要理解什么、先做什么、怎样验收？再看实际页面，是否出现一整屏没有视觉停顿的连续文字？有则重新组织。

各节按内容选形式，不要求机械复制同一模板，也不把全文改成只有术语的清单。列表前后保留必要的情境与解释，避免大量嵌套。已有文章局部更新时，保留成立的判断、提示词与代码，不重写无关内容。

## 3. 语言具体、平实，结论带上条件

- 先用常见语言解释概念，再给必要的英文名称或缩写；同一术语在全篇保持一致。中文与 Latin 名称之间保留适当空格。
- 写清“谁在什么情况下，执行什么动作，产生什么结果”。少用“赋能、代际颠覆、终局、必然、彻底解决、永远最新”等无法验证的表达。
- 区分业务目标、技术约束、假设设计与实测结果。示例数字注明是预算、目标或测量，不能把教学案例写成已上线产品的数据。
- 不把框架能力、提示词、模型名称、Temperature 或架构标签写成可靠性保证；说明应用仍需负责的校验和边界。
- 工具推荐解释适用条件、替代方案与维护成本；不把工具清单当成必装套餐，不为追新插入无关型号或价格。
- 不写没有依据的百分比、排名、成本收益与性能承诺。对不确定内容说明缺失的证据及验证方式。

文章正文面向读者，不混入本仓库文件路径、构建日志、发布过程或本轮对话。工程执行证据另存 `docs/exec-*`。当内容本来就是部署教程时，必要命令与路径属于教学内容，应完整保留。

## 4. 示例、提示词与交付物要能直接使用

优先选一个与本篇有关、规模足够小的案例贯穿全文。引入时说明目标、输入、结果和假设；后续各节沿同一案例增加细节，不频繁切换到互不关联的产品。

在涉及可靠性、权限或外部写操作时，至少解释一个失败路径。区分“模型说完成”与“业务状态确实完成”，写明证据和接管方式。

提示词放在使用环节附近，采用现有 `prompt` 围栏；包含必要上下文、输入槽位、目标、约束和输出要求。要求 AI 区分事实与未知，不能通过提示词自动宣布验收通过。JSON、契约、代码和命令保留可选择文本，不截图替代。

面向使用 Coding Agent 的读者，要区分建设者与 Agent 的职责：建设者确认真实问题、优先级、约束与可接受结果，Agent 检查代码、解释缺口、实现并验证。提示词优先围绕一项具体升级，给出与用户问题对应的验收，避免只要求“全面企业级改造”。

交付物应能被检查，例如范围说明、契约、对比记录、评测报告或恢复流程。与下一阶段交接时，说清需要带走的决定、证据和未知项。

涉及生产化、性能或长任务时，写清负载类型与计时边界：受理、模型首 Token、用户首个有效内容、完整完成分别定义。解释并发、队列、限额与长尾的相互影响；分段案例保留原始时间、覆盖、失败恢复和部分结果语义。不把异步、流式、分段或增加 Worker 本身当成已经验证的提速。

## 5. 研究与引用遵循证据范围

技术事实优先核对官方文档、官方仓库、原始论文和标准原文。涉及版本、平台组合、价格或现行规则时，核对具体版本与日期；无法查证的判断保持为候选，不凭记忆补成事实。

链接紧邻其支持的论点，使用有含义的来源名称，不使用裸 URL 或搜索结果页作为引文。区分来源直接支持的事实与作者的工程建议，避免一份引用看起来为整个长段落背书。必要时在导读注明资料核对日期。

用户提供的研报、视频摘要和转述是线索。没有原视频，不保留看似精确却未核验的时间戳；没有原始证据，不把个人意见写成行业统一标准。全文以自己的解释组织，避免长段复制来源。

## 6. 先选表达形式，再决定是否画图

每一幅图先写一句“这幅图要回答什么问题”，并记录所在段落、形式与边界，维护在 [content-map.md](diagrams/workbench/content-map.md)。只在图能比文字更清楚地展示关系、次序、分支或边界时添加。

| 要表达的内容 | 优先形式 | 检查重点 |
| --- | --- | --- |
| 职责、能力或层级关联 | 分支图、思维导图 | 不把无先后关系的分支画成步骤 |
| 系统连接、资源访问、可信范围 | 拓扑、边界图 | 框表示真实包含；连线说明访问或数据方向 |
| 不同起点进入共同过程 | 合流图 | 各起点有自己的动作，合流有明确共同成果 |
| 用户完成任务的连续过程 | 旅程或时间线 | 顺序有意义，保留核心结果与失败入口 |
| 条件、放行与修订 | 判断流程或发布门禁 | 条件有对应结果，回路有明确去向 |
| 请求、响应、超时与恢复 | 时序图 | 参与者、时间顺序、成功事实和未知状态分开 |
| 选项、标准、职责、验收维度的比较 | 可选择的 Markdown 表格 | 列的比较尺度一致，不把整张表再画成图片 |
| 真实测量与变化 | 有数据来源的数量图 | 单位、样本、时间与轴清楚；无数据不画比例或排名 |

不强制每节插图，也不要求所有图都用不同引擎。避免反复使用三栏分组框、装饰性卡片、无含义箭头，以及与正文不符的模板。图适合不了所在段落时，应重画或删除。

## 7. 沿用本站图表样式与 SmartDiagram 流程

统一白底、纯中性灰、细线图标、衬线图题与无衬线标签。当前色值为 `#ffffff`、`#f9f9f9`、`#d9d9d9`、`#838383`、`#646464`、`#202020`；具体用途、字体栈、1040 单位画布和两倍 WebP 导出沿用图表规范。不私自加入彩色标题栏、渐变、阴影、emoji 或装饰外框。

图题说明关系，标签短而明确。箭头有方向含义；实虚线、框与位置的含义要能从标签或图注理解，不用灰度深浅伪装数值。中英文分别排版，不按中文长度估计英文空间。

使用 `G:\project\SmartDiagram` 时先读其说明并核对实际引擎输入。保存对应的 Mermaid、Draw.io、Flow JSON、Mindmap 或 Infographic 等编辑源，图集同时保留 SVG、WebP 和清单。当前网站流程实际复用 SmartDiagram 的 Mermaid 清洗器，再用原生 SVG 排版和 sharp 导出；必须如实描述，不能声称是未运行的 AI 生成或画布导出。

尽量复用本站 `scripts/notes-diagrams/`。按文章定向再生成，避免无关旧图变化。所有图片都须检查英文换行、文字与连线相交、裁切和字号。先确定画面，再把最终图片接入正文。

每幅图前保留必要的场景引导，图后保留一句边界或关键解释。alt 概括图的核心含义；沿用图片本身可点击及“查看原图 / View full-size”的入口。关键规则、指标和提示词仍以文字可读，不只存在于图片。

## 8. 双语、命名与站点入口同步

Workbench 系列使用 `【AI 开发工作流 · 0X】 中文标题` / `【AI Dev Workflow · 0X】 English Title`，编号跟随阶段，不因文章发布日期重排。文件首行 H1 保存完整文档标题，进入 CMS 或回退正文时去掉重复 H1。

正文源为 `docs/notes/<slug>.zh.md` 与 `.en.md`（历史文件沿用已有命名）。中文先明确内容，再写自然英文；概念、步骤、事实、引用、图示含义和关键提醒对应，允许为语言习惯调整句长。不得出现英文缺节、中文改图后英文仍用旧图等情况。

列表与 Workbench 沿用英文展示；详情保留中英文切换。新增文章需同步双语标题、摘要、标签、正文、Notes 回退和 Workbench 的阶段入口及资源卡片。同一提示词在英文正文和资源卡片中保持一致。

新插图本地预览使用实际存在的 `public/notes/<slug>/` 路径；外部公开资产只有上传并验证后才能写成其可用地址。不要先填一个尚未存在的 R2 URL。沿用内容哈希命名，保留正式历史对象；新增本地图片后更新尺寸索引。

CMS 与静态数据分别核对。成功读取 CMS 时，Workbench 不会自动合并静态新增阶段。明确本轮交付属于本地准备、内容发布还是应用部署，禁止把其中一种写成另一种已完成。

## 9. 完稿和发布前核对

1. **内容：** 目标明确、叙事连贯、案例一致、实际页面可扫读；入门读者能说明全文的主要能力分支及其关系，而不仅是记住术语；重要判断有适用条件，假设与实测分开，读者知道下一步如何行动。
2. **来源：** 主要链接与具体论点对应，版本及日期准确，无未核验时间戳、虚构数据或过长摘抄。
3. **结构：** 标题层级、编号、列表和围栏闭合正确；提示词与代码可复制；TOC 的全部目标存在，重复标题 ID 唯一。
4. **图文：** 每幅图回答对应段落的问题；双语图、图题、alt、图注、正文和源文件一致；六色、字体与尺寸遵守规范。
5. **资产：** 图片可访问、格式与尺寸正确；本地路径存在，哈希清单与引用一致，不上传凭据、签名链接或迁移快照。
6. **页面：** 查看实际桌面和窄屏，检查语言切换、目录跳转、原图入口、图片可读性与整页横向溢出。受环境限制时记录未完成项，不用源文检查代替页面验收。
7. **入口：** Notes 列表、Workbench 文章与资源入口正确；从 Workbench 进入的返回目标仍为 Workbench，canonical 不带来源参数。
8. **工程：** 内容同步脚本和相关检查通过，`git diff --check` 无错误；改 React / TS 跑 lint，改媒体代码或静态清单按项目要求跑对应测试。只改文章不扩大测试范围。
9. **状态：** 记录本地、CMS、资产上传和应用部署各自的实际完成情况。仅用户要求时 commit / push；是否发布按当前授权范围执行。

## 10. 推荐的创作顺序

阅读相邻章节与本规范 → 明确本篇问题、成果与案例 → 核查官方资料 → 写叙事提纲和正文 → 判断图、表、列表的分工 → 生成并检查双语图 → 将图嵌入对应段落 → 同步英文与站点入口 → 进行内容和页面验收 → 记录发布状态。

这是一套判断与检查标准，不是要求每篇文章套相同模板。以后修订标准时，在本文统一更新；`AGENTS.md` 保留简短入口，图表细则保留在图表规范中，避免维护多个互相冲突的版本。
