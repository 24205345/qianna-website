# 【AI 开发工作流 · 05】核心功能开发与迭代：先做出来，再一步步完善

> [上一章](https://www.qiannawang.com/notes/ui-prototype-ergonomics)做出了能点击的原型。这一章，让按钮背后的功能真正运行起来。

## 1. 这次只做核心功能

继续用前面的**知识问答工具**举例。这一轮，要把能点击的原型做成能完成一次练习的工具。下面是从确定范围到开发、试用和扩展的顺序；案例仍用于讲方法，不代表已经上线的产品。

本轮的核心功能，就是把这四步做完整：

**粘贴材料 → 生成三题 → 回答题目 → 查看解析与原文。**

第一版先不做个人中心、社区、支付和跨设备历史记录。先回答一个问题：**用户能不能拿一份材料，完成一次有用的练习？**

这里沿用前几章的决定：题目和答案保留在当前页面，关闭后不保证恢复。需要下次接着学，再加入保存记录；如果产品一开始就处理多人的私人材料，登录和权限就不能省。

先把前面做好的三份资料交给 AI，让它读清楚这次要做什么：

1. **需求文档：** 这次做什么，暂时不做什么。
2. **方案与接口说明：** 前后端怎样配合，输入和结果长什么样。
3. **UI 原型：** 页面怎么摆，点击后显示什么，失败时怎么办。

有现成代码的，也一起提供。有不清楚的地方，先让 AI 提出来，确认后再往下做。**本轮范围说清楚了，接下来先准备项目、提交已有改动，再开始开发。**

## 2. 开发前先保存代码

上一节确定了“这次做什么”，现在准备动代码。**养成一个习惯：正式开发前，先把之前的所有改动检查并提交到 Git，再开始写新代码。** AI 一次可能修改很多文件，提前提交，改坏了才有一个明确的版本可以退回。

根据你的起点，先把项目准备好：

- **已经有项目：** 先启动一次，确认原来的功能能用。
- **从零开始：** 让 AI 用官方脚手架搭好目录和启动配置，确认基础项目能启动。

如果要接入模型服务，也在这时准备好 API Key，提交前分清哪些配置能进 Git：

- **真实密钥**放在服务端的 `.env` 等本地环境配置里，把对应文件加入 `.gitignore`，不写进页面代码，也不提交到 Git。
- **`.env.example`** 只写配置名称和占位值，方便以后照着填写。
- **不确定怎么填**，让 AI 说明文件位置和填写方式，不用把真实密钥贴进聊天。

注意：已经提交过的密钥文件，后来再加进 `.gitignore` 也不会自动消失。见 [Git 官方说明](https://git-scm.com/docs/gitignore)。

**项目和配置准备好后，检查改动，再完成提交：**

```powershell
git status --short
git diff
git diff --cached
```

这三条命令是用来查看改动的，还没有提交。看不懂输出也没关系，让 AI 解释改了哪些文件，确认没有混入密钥等不该提交的内容，再把此前的改动提交到 Git。**完成这次提交后，才进入下一节的功能开发。**

以后每完成一个能正常使用的功能，也提交一次。每次扩展前同样先提交既有代码。不要直接让 AI“清空所有改动”来恢复项目。

## 3. 让 AI 分步开发

不要等 AI 写完一大堆代码，才第一次打开项目。可以按下面的顺序，每做完一步就运行一次：

1. **先显示题目。** 把原型中的固定题目从后端返回，确认前后端接得上；这时还没有真正调用模型。
2. **再接入模型。** 用一份材料生成真实题目，检查三道题和选项是否完整。
3. **接通作答。** 选答案、提交、看解析，再打开原文，回来后答案还在。
4. **补上失败提示。** 空材料不能提交；生成失败保留输入，让用户可以重试。

下面这段可以作为开发的起始提示词：

```prompt
请阅读 @需求文档 @方案与接口说明 @UI原型 @当前代码。

开发目标：粘贴材料 → 生成三题 → 作答 → 查看解析与原文。
本次不增加登录、社区、支付或跨设备同步。
题目和作答只需在当前页面保留。

先给我开发步骤和需要确认的问题，计划确认后开始。
按上面的顺序分步实现，每做完一步就运行检查。
页面遵循提供的原型，缺少的状态先指出来。
按项目实际版本查 Context7 或官方文档，不凭记忆猜 API。
关键功能先写测试再实现；写完后启动项目，自己走一遍流程。
缺少密钥或无法运行的检查，要明确告诉我。

交付时告诉我：怎么启动、怎么填写配置、测过什么、还有什么没完成。
```

[Context7](https://github.com/upstash/context7)可以帮助 AI 查文档。这里要查的是项目正在使用的版本，不是顺手把所有依赖升级一遍。

**如果某一步卡住，就只处理这一小步：**

```prompt
这次只完成：[具体功能]。
操作：[输入什么，点击哪里]。
结果：[应该看到什么]。
失败时：[应该提示什么，保留什么]。

先检查已有代码，只改这一步需要的地方。
完成后实际运行，并告诉我检查结果。
```

## 4. 先让 AI 自己测试

**AI 写完代码后，应该先自己运行、自己检查、自己修错，再交给你。** 不能只说“代码已经生成，请自行测试”。

本例至少让它检查这几件事：

- **正常输入：** 能生成三道完整题目，提交答案后能看解析。
- **空白输入：** 直接提示补充材料，不调用模型。
- **生成失败：** 显示错误，原材料还在，可以重试。
- **查看原文：** 打开再返回，不丢掉刚才的答案。

其中，输入限制和题目数量等明确规则，可以让 AI 写成自动测试，以后改代码时重新运行。能控制浏览器的 AI，还可以用 [Playwright](https://playwright.dev/docs/best-practices)模拟填写、点击和返回。

**TDD 是什么？** 就是先写测试，再写功能。以“空材料不能出题”为例：

1. 先写一个测试：提交空材料，应该收到提示，而且没有调用模型。
2. 运行测试，确认现在还做不到，再补上输入检查。
3. 重新运行，确认通过；以后改代码，也继续检查这条规则。

模型调用可以先用固定结果代替，方便反复测试；但这还不能说明真实服务能用。配置好密钥后，需要另外做一次真实调用。如果 AI 没法启动浏览器或缺少配置，就让它列出没测的地方，不能当成全部通过。

到这里，AI 应该给你一个**能启动的版本、一份测试结果，以及你可以照着操作的试用步骤**。

## 5. 再自己从头用一遍

AI 已经检查过了，你再亲自试一次。你要看的除了“有没有报错”，还有“这是不是我想要的功能”。

拿一份自己看得懂的材料，完成下面几个动作：

1. **完整做一轮：** 粘贴材料、生成题目、作答、看解析。答案能从原文找到吗？有没有瞎编？
2. **中途来回切换：** 看原文，再回题目，答案和位置有没有丢？
3. **试试不正常的输入：** 空材料会怎样？失败后能不能重新开始？
4. **用手机宽度看看：** 题目是否看得全，按钮是否点得到？

### 报错就直接贴给 AI

不用先学会读懂报错。把错误文字贴过去，补一句你刚才做了什么，就能开始排查。比如：

> 我粘贴材料后点击“生成”，一直转圈，最后显示“请求失败”。我希望失败后材料还在，现在却被清空了。下面是报错和截图。

需要更完整地描述时，可以复制这段：

```prompt
我手动试用时遇到问题，请帮我修复。

操作步骤：[输入什么，点击哪里]
我希望：[应该发生什么]
实际发生：[页面表现或错误文字，可附截图]

请检查代码和日志。信息不够就告诉我还需要看哪里，不要猜着大改。
修好后自己运行检查，确认原来能用的功能还正常，
再告诉我怎样重新操作，确认这个问题已经解决。
```

没有错误提示也能反馈：“等太久”“按钮没反应”“解析说反了”都可以。截图和日志里的密钥、Cookie、私人材料要先遮住。

**AI 修好后，你再按原步骤试一次。** 报错不再出现，原来的功能也还正常，这个问题才算解决。自己的材料试过以后，有条件再请一位目标用户独立操作，看看他是否也能顺利完成。

### 做完后留一张进度便条

让 AI 写下四件事：**怎么启动、已经做完什么、还有哪些问题、下一步做什么。** 对话太长或需要换新对话时，带上这份便条、最新文档和代码继续，不用靠聊天记住全部细节。

## 6. 一次只加一个新功能

核心功能能用了，再来做扩展。Scaling 可以先从很小的一步开始：**用户答错以后，能不能再练一道类似的题？**

**每次扩展新功能前，也要先提交既有代码。** 确认当前功能能正常运行，把上一轮的改动提交到 Git，再开始这一轮开发。这样新功能出了问题，就能回到扩展之前的版本。

这次只增加“再练一题”，先不顺便做错题本、学习计划和排行榜。

先把使用方式说清楚：答错后点击“再练一题”，用同一份材料出一道新题；原来的三题和作答保留。材料不够出新题，就明确提示，不能为了出题编造内容。

```prompt
现有三题练习已经能正常使用，请先读当前文档和代码。

这次新增：答错后，用户可以点击“再练一题”。
使用同一份材料生成一道相关题目，不覆盖原来的题目和答案。
材料不足时给出提示，不编造内容。

先说明要改哪些页面和接口，哪些现有代码可以复用。
方案确认后分步开发，不顺便重写无关功能。
做完后自己测试新题，也重跑原来的三题练习和失败重试。
```

**检查两件事：新功能能用，旧功能也没坏。** 尤其要试一次新题生成失败：原来的练习应该仍然可看、可继续。

每次完成一项扩展，测试通过后就提交代码、更新说明，再开始下一项。只有发现几个功能反复写相同逻辑时，再让 AI 整理共用部分，不急着搭一套庞大的“通用平台”。

## 7. 人多变慢再找原因

Scaling 的另一部分是：自己用挺好，几个人同时用却变慢了。此时先测清楚慢在哪里，再决定怎么改。

### 先看用户在等什么

一次生成至少有几个不同的时刻：点击按钮、服务收到请求、开始看到有用内容、完整结果出现。

<!-- /figure:build-timing -->

本例是三题一起返回，所以“看到第一题”和“全部完成”可能同时发生。以后改成逐题显示，可以让用户早点开始看，但不保证全部生成得更快。

| 遇到的问题 | 先让 AI 查什么 |
| :--- | :--- |
| 一个人用也很慢 | 是页面处理慢，还是一直在等模型？ |
| 几个人同时用才失败 | 同时请求是否太多，是否碰到服务限额？ |
| 点一次却重复生成 | 是否重复提交或自动重试，产生多次费用？ |
| 刷新或重启就丢进度 | 题目和任务进度是否只存在内存里？ |

### 找到原因再选办法

- **请求太多：** 可以限制同时处理的数量，让其余请求排队。排队只是安排先后，不会让每次出题变快；等太久时也要给提示。
- **重复做相同工作：** 可以考虑复用已生成结果，也就是缓存。但“重复点击”和“我要重新出一套题”含义不同，私人材料也不能串给别人。
- **任务需要很久：** 可以交给后台程序继续处理，页面显示进度。要想重启后继续，还得保存任务和结果，光把任务搬到后台不够。

这些办法都会增加开发和维护工作。先选能解决眼前问题的一个，改完后用同一份材料、相同人数再测，看看等待、失败和费用有没有改善，题目质量有没有下降。

```prompt
现在遇到的问题：[例如两个人同时生成时，经常失败]。
运行环境、操作步骤和日志：[附上]。

先帮我查清楚慢或失败在哪里，说明依据，不要直接加缓存或队列。
给一个最小改进方案，说明要改什么、有什么代价。
真实调用测试如果会产生费用，先告诉我规模和预算。
修改后，用同样的输入和人数比较前后结果，也检查题目质量。
```

需要跨次保存学习记录时，下一章再处理数据库和存储。需要长期供多人使用时，继续看[第八章](https://www.qiannawang.com/notes/enterprise-ai-production)的后台任务、权限与故障恢复。

这一章结束时，你应该能**从头完成一次真实练习，知道遇到错误怎样让 AI 修复，也知道下一项功能该怎么加**。
