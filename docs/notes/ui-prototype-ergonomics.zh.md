# 【AI 开发工作流 · 04】 UI 原型与交互体验：从产品流程到可用界面

> **这一章要完成什么？**
> [第三章](https://www.qiannawang.com/notes/architecture-contracts)明确了系统职责和接口约定。现在，把这些决定变成用户能看懂、能操作、遇到问题也知道怎么办的界面。

Agent 可以很快写出页面，但**页面能显示，不代表任务容易完成**。这一阶段先用可点击的原型检查流程、信息顺序和交互状态，再进入真实功能开发。

继续使用前两章的**知识问答工具**作为教学案例：用户提供材料，生成练习，回答题目，再查看解释与原文。这里的界面与数字是设计示例，不代表已经完成用户验证。

| 你需要决定 | 可以交给 Agent 做什么 |
| :--- | :--- |
| 用户先做什么，什么结果才有用 | 把任务拆成界面和状态，指出缺口 |
| 哪些内容优先，哪些可以稍后查看 | 按现有风格实现布局和组件 |
| 等待、失败、离开时应该发生什么 | 用模拟数据做出可体验的分支 |
| 怎样才算好用 | 实现后检查，再由真实任务试用验证 |

---

## 1. 从任务推导界面

先写出一句任务：**“我想根据这份材料练习，知道哪里理解错了，并能回看依据。”** 然后沿任务展开，不急着列首页、仪表盘、个人中心。

[![一个任务，四个界面时刻 — 界面围绕任务展开，不要求拆成四个独立网址。](https://media.qiannawang.com/notes/workbench-diagrams/v3/ui-task-pages.zh-e83b03632a70.webp)](https://media.qiannawang.com/notes/workbench-diagrams/v3/ui-task-pages.zh-e83b03632a70.webp)

*界面围绕任务展开，不要求拆成四个独立网址。 [查看原图](https://media.qiannawang.com/notes/workbench-diagrams/v3/ui-task-pages.zh-e83b03632a70.webp)*

**界面按任务组织，不必一个步骤一个页面。** 小工具可以在同一页切换状态；步骤较长、需要独立访问时，再考虑拆页。

- **提供材料：** 说明支持什么输入；有长度或格式限制，就放在输入处。
- **生成练习：** 输入仍可辨认，用户知道在等什么，也能取消或处理失败。
- **回答题目：** 当前题目、作答方式和提交入口清楚，解释不要提前泄露答案。
- **查看反馈：** 区分答对、答错与依据不足；查看原文后能回到原来的作答位置。

这份列表就是原型的范围。**没有进入本轮范围的账号、历史记录、支付，不因为模板里有就顺手加入。**

## 2. 建立信息与视觉层次

界面首先要回答三件事：**我在哪里、现在能做什么、做完会发生什么。** 先用线框检查，再调整颜色、留白和细节。

[![让下一步操作有清楚的位置 — 作答状态的线框示意；答案解释在提交之后出现。](https://media.qiannawang.com/notes/workbench-diagrams/v3/ui-reading-order.zh-39574b3d725b.webp)](https://media.qiannawang.com/notes/workbench-diagrams/v3/ui-reading-order.zh-39574b3d725b.webp)

*作答状态的线框示意；答案解释在提交之后出现。 [查看原图](https://media.qiannawang.com/notes/workbench-diagrams/v3/ui-reading-order.zh-39574b3d725b.webp)*

图中主要任务是作答，因此题目与选项占据阅读中心。材料属于按需查阅的信息；反馈在提交后出现。这样的先后关系比“每个模块都做成一样大的卡片”更值得先确定。

**把参考图变成明确要求**

不要只给 Agent 一张图并说“照着做”。指出要参考的部分，也说明必须保留的现有规则：

- **布局：** 参考左右分区，还是内容宽度与留白？
- **层次：** 标题、正文、注释如何区分？哪个操作最突出？
- **组件：** 沿用现有按钮、输入框、导航和提示方式，避免每页一套。
- **边界：** 参考图没有覆盖的手机、错误状态和长内容，需要另行设计。

原型可以使用现有组件库，也可以让 Agent 用项目已有技术实现。**先确认任务与状态，再决定是否引入新依赖。** GOV.UK 的[原型指南](https://www.gov.uk/service-manual/design/making-prototypes)说明了从纸面到代码原型的不同用途；选择能回答当前问题的精度即可。

### 先约定视觉方向

流程明确之后，还要说明页面应该呈现什么气质。Anthropic 的[前端美学提示指南](https://platform.claude.com/cookbook/coding-prompting-for-frontend-aesthetics)建议分别约定字体、配色、动效和背景，提供具体参考，并指出希望避开的通用模板倾向。

对本章的知识问答工具，可以把“安静、适合阅读”写成下面这份**视觉说明**。这些是案例中的设计选择，实际项目应替换为自己的规则。

| 设计方面 | 可以交给 Agent 的具体要求 |
| :--- | :--- |
| 字体与排版 | 沿用项目字体；用标题、正文、注释建立三层关系，长题目自然换行，正文宽度与行距适合阅读 |
| 布局与留白 | 桌面把作答作为主区域，材料按需查阅；手机先题目后材料，相关信息靠近，段落间留白一致 |
| 配色与背景 | 沿用浅底、中性灰和细分隔线；主操作清楚，错误与选中状态同时用文字或形状表达 |
| 动效与反馈 | 动效帮助解释视图切换或面板出现；作答区位置稳定，减少动态效果时直接显示最终状态 |

**已有产品先继承设计规则。** 指南中的字体名单、强字号对比和背景效果属于示例取向。本站继续沿用既有双字体和中性灰风格；中文另查字形覆盖、回退字体和中英文混排，不能仅凭英文样张决定字体。

### 从参考页提取规则

看到喜欢的页面，先指出具体哪里有帮助。 [Refero Styles](https://styles.refero.design/) 把网站样例整理成字体、配色、间距和组件规则，并提供 `DESIGN.md` 等格式。可以借它学习拆解方法，把“喜欢这种感觉”转成 Agent 能继续使用的视觉说明。

**观察一处，写下一条规则，再说明适用边界。** 以练习工具为例：

| 看到的设计 | 可以带回自己项目的要求 |
| :--- | :--- |
| 标题突出，正文安静 | 沿用项目字体，拉开标题与正文的层级；用真实长题目检查换行 |
| 相关内容靠近，组与组之间留白 | 题目和选项放在一起，原文依据按需展开；不照搬参考页的整屏布局 |
| 页面只有一个最醒目的操作 | 输入材料后突出“生成练习”，“使用示例”保持次要；补齐等待和失败状态 |

整理时保留三项：**参考来源、采用的规则、需要另行验证的情况。** 可以放进项目已有设计说明，或单独维护一份 `DESIGN.md`；文件名不重要，内容需要具体、可检查，并随实现更新。

Refero 的[样例说明](https://styles.refero.design/style/12255b63-e506-4bc1-a4cd-d05487de32f3)区分了归纳的样式、解释性建议和重建示例。它们可以帮助理解设计，不能当作品牌官方规范或原始组件代码。参考产品里的字体、按钮和色板也需要对照自己的项目选择。

```prompt
请为一个页面整理视觉说明，本轮先不修改代码。

- 页面与核心任务：[例如：回答题目，并按需查看原文依据]
- 现有页面／参考截图：[附上，标明参考布局、排版或氛围中的哪一项]
- 必须沿用的字体、色板、组件和内容：[附上]

先检查项目现有样式，再按字体与文字层级、布局留白、配色背景、动效反馈四方面，列出“具体对象、采用规则、验收方式”。把安静、精致等形容词转成可观察的决定，未知项标为待确认。

同时说明桌面与窄屏的内容顺序、长中文标题与正文的换行、键盘焦点及减少动态效果的处理。列出需要保留的正文、截图和正常行为；没有必要时沿用现有字体和依赖。

交付一份可供后续原型实现使用的视觉说明，记录参考来源、采用规则和待验证项，区分参考图直接支持的要求与自行提出的建议。优先更新项目已有设计说明；需要时整理为 DESIGN.md，不把参考产品的整套风格直接覆盖到现有项目。
```

## 3. 把效果描述清楚

“高级一点”“加点动效”很难验收。新手也不需要先记住所有组件名，可以使用这个顺序：

**对象 → 触发 → 变化 → 结束与边界。**

> **模糊：** 卡片动一下。  
> **具体：** 鼠标悬停在练习卡片上时，用 200 ms 向上移动 4 px，并加深边框；移出后复原。键盘聚焦用轮廓提示，触屏直接打开条目。开启减少动态效果时取消位移。

这里的时长与距离只是演示参数，可以调整。它们描述视觉过渡，不代表业务请求会在 200 ms 内完成。

### 说清一个操作入口

“按钮明显一点”还缺少用途。行动入口（Call to action，简称 CTA）需要让人判断：**点什么、点完发生什么、哪个操作优先。** [CTA.gallery](https://www.cta.gallery/) 收集按钮、表单、下载等入口，可以观察文案、位置和主次关系；案例偏营销场景，不能仅凭收录就推断转化效果。

在练习工具中，先比较同一份材料下的两个入口：

| 比较步骤 | 要观察什么 |
| :--- | :--- |
| “继续 / 试一下”改成“生成练习 / 使用示例” | 不用先点击，能否判断下一步会发生什么 |
| 明确文案后，再突出“生成练习” | 第一眼能否找到主要操作；次要操作是否仍能辨认 |
| 实际点击，检查等待和失败 | 能否避免重复提交，失败后材料是否保留，重试入口是否清楚 |

可以这样描述：**材料输入区后突出“生成练习”，“使用示例”作为次要操作。生成期间说明正在处理并避免重复提交；失败后保留材料，提供重试入口。** 文案、视觉优先级和请求状态分别检查，不能靠加深按钮颜色解决全部问题。

### 一次聚焦一个维度

同一份指南也演示了[只调整字体或固定主题](https://platform.claude.com/cookbook/coding-prompting-for-frontend-aesthetics#isolated-prompting)的提示方式。本章把它用于有边界的迭代：**先确定要改善什么，再比较改动是否有效。**

1. **固定基线：** 用相同内容、状态和视口保存修改前的页面；保留桌面与窄屏各一份。
2. **限定本轮：** 例如“只调整题目页的文字层级和段间距，沿用布局、配色、按钮与作答行为”。不把“优化字体”顺带扩大为整页重做。
3. **对照检查：** 改动后看主次是否清楚、长中文是否溢出、手机是否可读，再走一次作答与查看原文的流程。记录实际观察，不用“更高级”代替验收。

接下来用实验室把这些决定与可操作的示例对应起来。

### 动手试：界面交互实验室

**[打开交互实验室 →](/notes/ui-prototype-ergonomics/interface-lab.html?lang=zh)**

实验室按“左侧选风格、中间看效果、右侧说需求”排列。左栏沿用参考文件的四块设置：经典风格预设、页面布局、组件与视觉、动效与物理参数。调整会直接作用于同一个预设网页，并保留当前预览位置；导航、首屏与组件示例保持连续，项目资料、阅读笔记和练习工作台在页面内切换。示例在页面内运行，不发送模型请求，也不持久保存输入与设置。

部位知识按六类问题整理，共有 24 个按需打开的交互对照：

| 从什么问题开始 | 可以比较什么 |
| :--- | :--- |
| 页面怎样分区 | 完整页面、单栏与主次分栏、侧栏、卡片／列表／表格 |
| 怎样容易阅读 | 文字层级、行长与留白、强调色与状态色、图片比例与裁切 |
| 怎样找到信息 | 页签与页内定位、搜索与分类、排序与分页、折叠与展开 |
| 怎样完成操作 | 表单校验、单选／多选／开关、下拉与搜索选择、弹窗／抽屉／弹出面板 |
| 等待或失败后怎么办 | 加载与进度、空内容与无匹配结果、失败重试、AI 分段输出与中断 |
| 换个屏幕怎样使用 | 窄屏顺序、吸顶与滚动、淡入与位移、文字放大与减少动态 |

开启顶部的“X-Ray 部位透视”，悬停或点选预览区域，查看中文名称、英文术语和需求句；小标签只在悬停、聚焦或选中时出现。右侧“部位词典表”可搜索 34 个页面与组件词条。选中带有交互示例的部位后，展开“用途与交互示例”，只查看这个部位的比较选项、适用场景和操作规则；需要时点击“在预览中定位”。关闭透视后，可以观察没有标注的页面效果。

**按“试一试 → 观察 → 命名 → 描述”使用：**

1. 在左侧选择一套风格预设，再调整布局、视觉或动效，观察原网页怎样变化。预览中的导航和行动按钮能进入资料、阅读与练习区域；表单可以留空提交，搜索可以输入无匹配词，生成任务可以暂停、继续或取消。
2. 想比较具体交互时，用透视或词典选中对应部位，再展开右侧“用途与交互示例”。选择一种呈现并操作，用这里的“修改前／修改后”比较所选部位，或用“设为对照”保留基线。比较会保留输入、选择和其他设置。
3. 结合名称、用途和操作结果，选择输出“整页需求”“当前部位”或“本次调整”。提示词可用中英结构版或纯英文版，默认沿用现有项目技术栈；复制后替换占位内容。

“画布宽度”改变实际排版空间，可选择适应窗口、960、768 或 390 px；75%、85%、100% 只改变显示比例。用手机画布比较主任务与资料目录的先后，再核对输入仍在。右侧修改前后的对照只作用于所选部位的设置，不包含风格预设、窗口宽度和正在进行的任务状态。

风格区保留 Linear、Gumroad、AntD、Apple 四套起始预设，以及布局、组件库气质、材质、强调色、圆角与动效设置。“附加组件”展示骨架屏和轻提示的样式样本；任务的加载、失败和中断比较通过对应部位打开。生成按钮位于材料输入框右下角，等待时可在同一位置暂停或取消。弹簧预览使用 CSS 近似，只有勾选“加入可选技术参数”才将 Framer Motion 参考参数写入需求，成品仍需验证。AI 示例按固定阶段返回练习模板，用于观察状态，不实际理解材料。

组件库风格与表面材质可以分别选择：前者改变控件形态、间距与层级，后者改变填充、透光、模糊和装饰投影。用同一种材质比较 shadcn/ui、Ant Design、Material UI，再固定组件风格切换材质，更容易说清差别。这些是 CSS 视觉示例，不等同于完整组件库实现。主色支持预设色、自定义取色与色相滑杆，当前色值同步到需求文本；改配色不清空已输入的内容。

**先描述整个页面，再描述局部控件。** 页面需要交代信息顺序、主次区域和阅读节奏；组件描述再补充具体触发与状态。

| 页面层面 | 需要描述的效果 |
| :--- | :--- |
| 布局 | 主次双栏、等宽双栏与单栏；桌面分屏和手机材料展开 |
| 页面收尾 | 同一组页脚链接平铺或按用途分组；随内容排列，不遮挡正文 |
| 文字与排版 | 衬线或无衬线标题、字号层级；行高、段间距和最大行宽 |
| 页面动效 | 滚动进入时淡入或短距离上移；视图切换时保留导航与焦点 |

试着把“做得精致一点”改成：**桌面用主次双栏，标题为衬线体，正文保持舒展行距；手机合为单栏。次要章节首次进入可见区域时短距离淡入，系统要求减少动态效果时直接展示。** 然后再补充下面这些组件规则。

| 想表达什么 | 常用名称与需要说清的规则 |
| :--- | :--- |
| 下一步点哪里、点完做什么 | CTA：具体文案、主要与次要操作、操作后的状态 |
| 按钮能不能点、正在处理什么 | Button：默认、悬停、聚焦、禁用、加载 |
| 一组内容轻微浮起 | Card：触发方式、位移、边框、复原 |
| 填写错误后怎么纠正 | Input：校验时机、错误文字、保留输入 |
| 在同一区域切换内容 | Tabs：当前项、键盘切换、草稿保留 |
| 点开再看次要信息 | Accordion：展开范围、是否允许多项 |
| 不离开当前任务查看详情 | Modal / Drawer：位置、遮罩、关闭、焦点返回 |
| 说明操作结果 | Inline status / Toast：位置、内容、何时消失 |
| 先展示部分 AI 结果 | Streaming / Progress：部分与完整、暂停、失败、取消 |

**先说明用途，再选择组件。** 一条持续阻止用户继续的错误，应该留在相关操作附近；不能只闪过一条很快消失的提示。抽屉也不天然比弹窗好，要看用户是否需要同时参考背景内容。

实验室演示的是页面与组件的常见行为，**不能直接替代项目完整设计系统**。复制描述时，把“练习卡片”换成实际对象，并删掉不适用的规则。

### 带着问题找参考

除了前面的 Refero Styles 和 CTA.gallery，还可以按当前问题选择资源。看完应留下一条自己的需求，避免只收藏截图。

| 需要解决的问题 | 观察什么，留下什么 |
| :--- | :--- |
| 页面最后放哪些信息 | 在 [Footer.design](https://www.footer.design/) 观察页脚的文字与分组，列出需要保留的导航、联系或说明入口；主操作仍留在主内容区 |
| 滚动时某个对象怎样变化 | 在 [Scrolltide](https://www.scrolltide.co/) 选择一个局部效果，记录对象、触发、运动方向与结束状态，再补齐触屏和减少动态效果的处理 |
| 背景效果是否帮助表达 | 在 [Scroll Shaders](https://scrollshaders.com/) 观察动态背景，先用自己的正文检查对比度、注意力和静态替代，再决定是否采用 |

后两项适合有明确需要时进阶探索。先把任务、内容层级和失败恢复做清楚，再考虑滚动或背景效果；预览能播放不代表自己的设备与页面已通过性能验证。

**参考方法与素材授权分别核对。** 实验室没有嵌入上述参考站点的模板或着色器。Scrolltide 的[使用条款](https://www.scrolltide.co/terms)和 Scroll Shaders 的[授权说明](https://scrollshaders.com/license)区分成品项目使用与资源再分发；若要复制代码、下载素材或提供可复用示例，需要按具体资源核对权限。上述公开资料核对于 2026 年 11 月，不把会变化的资源数量或价格写成选用依据。

## 4. 降低操作负担

“少点几下”和“每屏塞更多内容”都需要结合任务判断。自动生成可能节省一次点击，但如果会上传私人材料或产生费用，就应在触发前让用户知道，并按产品规则确认。

对于问答工具，可以这样取舍：

- **让用户少找：** 材料、当前题目与进度的位置稳定；提交后在附近显示反馈。
- **让用户少记：** 查看原文时保留当前选择，返回后不用重新填写。
- **让用户少猜：** “提交答案”比“继续”更清楚；处理中的按钮显示动作状态。
- **按需展开：** 把解释、完整材料等次要内容收起，同时保留能被发现的入口。

[![屏幕变了，任务顺序不变 — 次要材料面板可以收进抽屉；当前作答不能因切换而丢失。](https://media.qiannawang.com/notes/workbench-diagrams/v3/ui-responsive-order.zh-bc9f52d2a6a1.webp)](https://media.qiannawang.com/notes/workbench-diagrams/v3/ui-responsive-order.zh-bc9f52d2a6a1.webp)

*次要材料面板可以收进抽屉；当前作答不能因切换而丢失。 [查看原图](https://media.qiannawang.com/notes/workbench-diagrams/v3/ui-responsive-order.zh-bc9f52d2a6a1.webp)*

桌面可以并排展示题目与材料；手机优先展示题目，再按需打开材料。**响应式设计要保留任务顺序，不能只把桌面缩小。**

**至少亲手检查一次**

- **键盘：** 能依次到达控件，知道焦点在哪，关闭浮层后能回到原处。
- **触屏与窄屏：** 不依赖悬停才出现关键操作；按钮可操作，正文无需整页横向滚动。
- **可理解性：** 错误有文字说明，选中与完成不能只靠颜色区别。
- **动态效果：** 尊重系统的减少动态效果设置，关闭动画后状态仍然清楚。

这些检查对应 [WCAG 2.2 的键盘、焦点、重排与状态消息要求](https://www.w3.org/WAI/WCAG22/quickref/)；完成几项检查不等于已经满足整个标准。减少动态效果可以通过浏览器的 [`prefers-reduced-motion`](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion) 媒体查询适配。

## 5. 设计等待与失败

AI 页面很容易只画“输入”和“漂亮的结果”。原型需要把中间过程也做出来，才能发现用户会不会重复点击、误以为完成，或者因刷新丢掉材料。

| 状态 | 用户应该看到、能够做什么 |
| :--- | :--- |
| 没有输入 | 知道支持的材料与下一步；可给一份示例 |
| 校验不通过 | 在输入附近看到原因；保留已填内容 |
| 处理中 | 看到真实可获得的状态；防止重复提交 |
| 部分结果 | 明确尚未完成，缺少哪些部分，不伪装成最终报告 |
| 完成 | 看到结果与下一步，而不是只弹一个成功提示 |
| 失败或取消 | 知道哪些成果保留，如何重试，会不会再次收费 |

**不要编造进度。** 后端只能确认“已受理、正在生成”时，就展示这两个状态；没有总工作量依据，不展示看似精确的百分比。实验室的进度明确标为本地模拟。

**流式展示不等于处理已经更快。** 它可以让内容逐步可见，但要分别验证首个有用内容出现的时间和完整完成时间。长任务的队列、后台运行与恢复机制，留给[第八章的生产化升级](https://www.qiannawang.com/notes/enterprise-ai-production)；这一章先把用户能看到与能操作的规则定义清楚。

例如生成测验失败后，保留材料并提供重试。**原型中的“取消”只能说明期望交互；真实取消能否终止服务端任务、费用如何处理，仍要回到接口契约确认。**

## 6. 让 Agent 做可点击原型

输入给 Agent 的材料应当包括：**核心任务、范围、接口契约、现有视觉参考，以及刚才确定的状态规则。** 第一版使用可控的模拟数据，先让整条路径走通。

```prompt
请在现有项目中制作一个可点击的界面原型。

输入材料：
- 产品需求与本轮范围：[附上]
- 系统架构与接口契约：[附上]
- 现有页面参考与组件：[附上]
- 核心任务：提供材料 → 生成测验 → 作答 → 查看解释与原文依据。

先检查现有界面模式，在修改前说明计划采用的页面、状态和待确认问题。保留已有正文、截图与正常工作的功能。

使用明确标识的模拟数据实现本轮流程。按适用情况包含空白、输入不合法、处理中、部分结果、成功、失败和取消状态，并提供主动切换模拟场景的入口。不调用真实付费服务，不把原型写成已完成后端集成。

查看材料时不能丢失作答草稿。明确桌面与窄屏布局、键盘焦点及减少动态效果时的替代行为。模拟数据与界面分离，方便后续替换为真实接口。

交付可运行原型、状态清单与尚未解决的契约问题。验证主要任务和一条失败路径，说明实际检查内容与剩余缺口。
```

**把交互描述补在具体组件旁边。** 从实验室复制一段适用的描述，比在总提示词里塞十种不相关动画更有效。

原型跑通后，拿第三章契约核对三件事：界面要求的数据是否存在、错误能否区分、取消与重试的含义是否一致。**Mock 能演示的行为，不代表真实服务已经支持。**

## 7. 用真实任务验收

先自己完整走一遍，再让一位接近目标用户的人试用。给任务，不提前教每一步怎么点；记录卡住的位置、误解的文字和不得不返回的操作。

可以这样布置试用：**“用这份材料完成一次练习，找出一道答错题的依据，再回到练习。”** 关注任务是否完成、哪里需要解释；没有实际测量，不宣布“效率提升”。

```prompt
请用一个任务检查这个原型：使用提供的材料完成测验，查看一道错题的原文依据，再返回练习，过程中不能丢失进度。

检查实际运行的界面与相关接口契约。覆盖正常流程、生成失败、取消与重试、长内容、窄屏、键盘导航和焦点返回。区分观察到的行为与假设；没有亲自执行的检查不能写成通过。

按对任务完成的影响排列问题。提出最小必要修正，保留已有内容与正常行为。返回检查证据、未决问题及真实接口接入的交接清单。不能代替真实用户宣布用户验证已完成。
```

**交给下一阶段的成果**

1. **可点击原型：** 能完成一次任务，也能进入失败分支。
2. **页面与状态说明：** 谁触发、显示什么、能做什么、何时结束。
3. **组件与布局决定：** 沿用哪些现有组件，手机如何调整，草稿如何保留。
4. **试用记录与未决项：** 哪些问题已观察到，哪些仍需真实接口或用户确认。

下一阶段再接入真实功能与数据，按相同场景逐项替换 Mock，并重新验证。**原型阶段最有价值的产出，是让实现者与使用者对“应该发生什么”形成同一份可检查的理解。**
