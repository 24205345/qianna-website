# 从零到一：Qianna Wang 个人作品集网站全栈实录

> 一篇心得与教程结合的长文：分享我如何把 [www.qiannawang.com](https://www.qiannawang.com) 从静态展示页，逐步做成可以在后台更新的个人网站。包括内容取舍、视觉风格、页面组织，以及与 AI 协作、上线和持续维护的经验。

## 前言：为什么要做这样一个网站

个人作品集可以做成一页介绍，也可以做成在线简历。我更想要第三种：**小型档案库与期刊式的阅读体验**。

- **对外：** 安静、可以慢慢读，像打开一本整理过的速写本和研究档案。
- **对内：** 通过内容管理后台（CMS）修改文章、作品和图片，不必每次都改代码、重新发布网站。
- **实现上：** 用 AI 协助搭建，先把内容和页面做好，再按需要补充编辑、存储和统计等功能。

这个网站同时承担四种角色：

| 角色 | 说明 |
| --- | --- |
| **作品集** | Projects 和 Traces 展示项目、摄影、绘画与旅途中的观察 |
| **写作平台** | Notes 记录技术笔记、工具实验和建站经验；Workbench 将相关文章与资源整理成工作流程 |
| **个人名片** | About 介绍背景、经历和关注领域，首页用简短文字建立第一印象 |
| **轻量互动** | Guestbook 接收留言，审核后公开；访问统计帮助我了解哪些内容被打开 |

这些用途决定了网站的样子。如果只是为了让别人快速了解自己，一页简介和几个代表作品就可以开始；如果希望持续记录，内容的分类、阅读和更新方式就需要多想一步。

搭建个人网站时，可以用 AI Agent 工具辅助实现：用自然语言说明需求，让它协助编写和修改代码，再通过预览和实际操作不断调整。展示什么内容、呈现什么风格，以及效果是否符合需要，仍由自己决定。

## 站点定位与内容策略

### 2.1 内容模块划分

这些栏目并不是一开始就规划齐全的。随着工作的深入，我想在网站上发布的内容越来越多，才逐步增加了新的模块。例如，用 Notes 记录经验与工具实践，再用 Workbench 把相关文章、提示词和资源整理成工作流程。

现在的主要栏目如下，每类内容有不同的更新节奏，也需要不同的阅读方式：

| 模块 | 路径 | 内容性质 | 更新频率 |
| --- | --- | --- | --- |
| **Notes** | `/notes` | 中英双语长文、经验与工具笔记 | 不定期 |
| **Projects** | `/projects` | 研究、建筑与数字产品，按项目展开 | 项目完成或有新进展时 |
| **Traces** | `/traces` | 摄影、绘画与户外旅途记录 | 随材料积累 |
| **Workbench** | `/workbench` | 按步骤组织的文章、提示词和资源 | 随工作方法完善 |
| **About** | `/about` | 背景、经历与关注领域 | 低频 |
| **Guestbook** | `/guestbook` | 先审核、后展示的访客留言 | 随访客提交 |

栏目不需要一开始就齐全。可以先看手上的材料：哪些值得公开，哪些需要补文字，哪些足以独立成一个主题。材料少时合并展示，积累起来再拆分，会更容易维护。

### 2.2 首页叙事顺序

最初我把文章放在首页最前面，希望读者先看到最近在写什么。现在的顺序是：

**Projects → Traces → Notes → Workbench → About Me → Guestbook Preview**

先展示作品和观察，再介绍文章与工作方法，最后补充个人背景。这个顺序反映了我希望别人怎样认识自己。以写作为主的网站，可以继续把文章放在最前面。

首页只选取少量代表内容，各板块提供查看完整列表的入口。这样既能快速浏览，也给愿意深入了解的人留出路径。

第一屏的主视觉区通常叫 Hero。我使用封面图、标题、副标题和一个 `Enter →` 文字链接，让图片与简短介绍建立气氛。选择这种形式，是因为我希望读者进入一个可浏览的个人档案。

### 2.3 内容选择原则

1. **质量优先于数量。** Projects 不需要为了填满网格而增加项目；一条旅途记录也可以完整讲述一次经历。
2. **文字与图像并重。** 详情页先说明项目背景、自己的工作和成果，再用图片展开。不了解项目的人，也应能看懂它在做什么。
3. **按读者安排语言。** Notes 列表和首页以英文为主，详情可以切换中英文。双语也意味着持续维护两份内容，需要考虑自己的更新能力。

整理项目时，我会先选一张能代表它的封面，再写一段能独立理解的介绍。过程图、成果图和细节图各自承担说明作用；有必要的图片加上图注，让读者知道应该看哪里。

展示方式也跟着材料走。Thesis 这样的研究项目需要交代问题、过程与成果；早期 Xicaoshi 建筑项目侧重场地、设计和空间；Undergraduate Portfolio 是成册作品集，需要方便翻页与放大阅读。

旅途记录同样如此：南极洛、雨崩和滑翔记录以图库为主，滑雪记录则按文字、照片与视频的顺序讲述经过。先判断读者需要理解什么，再让 AI 安排版式。

## 视觉风格与设计系统

### 建站初期：找 UI 参考、定风格

动手写代码之前，我花了不少时间逛站、截图、整理“我想要什么感觉”。个人作品集很适合从**编辑感、留白多、图片说话**的网站里找参考，不必局限于设计师作品集。

我常会打开这些网站找灵感，按用途整理：

| 类型 | 去哪看 | 重点看什么 |
| --- | --- | --- |
| 高质量网页精选 | [Awwwards](https://www.awwwards.com/)、[Godly](https://godly.website/)、[siteInspire](https://www.siteinspire.com/) | 排版、动效是否克制、首屏信息密度 |
| 作品集与摄影 | Behance、Dribbble、建筑师或摄影师个人站 | 项目页叙事、图库节奏、About 页写法 |
| 期刊与博客 | Readymag、Cargo 上的个人站点、独立杂志网站 | 标题层级、区块间距、列表与长文怎样组合 |
| 组件与细节 | [Mobbin](https://mobbin.com/)（以 App 为主，导航和表单仍有参考价值） | 侧栏、标签页、移动端菜单 |

我的做法分为四步：

1. **截图并标注。** 圈出喜欢的文字粗细、颜色、卡片圆角、主视觉比例，也记下“这里太吵了”的反例。越能说明喜欢或不喜欢哪里，后续讨论越具体。
2. **写一段气质描述。** 例如：“暖灰色、衬线标题、按钮克制，像一本整理过的作品档案。”先给整站一个共同方向。
3. **和 AI 讨论。** 把截图和描述交给 Cursor，先讨论页面布局与首页顺序，再决定怎样实现。参考图里没有覆盖的手机布局和长内容，也需要一起考虑。
4. **先做一版预览。** 用真实文字和图片确认阅读顺序，看看照片比例、标题长度和留白是否合适，满意后再增加后台编辑功能。

参考网站帮助我提取留白、层级和阅读顺序等原则。最后采用的暖灰色系与衬线标题，是经过几轮截图讨论和页面预览后确定的。

可以这样向 AI 描述这一轮任务：

```prompt
我想做一个个人网站，主要展示【内容】，希望【读者】了解我的【特点】。
已有材料：【项目、图片、文章和简介】。

参考图 A：我喜欢它的【标题层次与留白】。
参考图 B：我喜欢它的【图片比例与内容排列】。
整体气质希望是【用几句话描述】。

请先讨论首页的内容顺序、页面布局和手机上的展示方式。
说明哪些参考适合我的材料，哪些需要调整；缺少的材料标为待补。
先给方案，暂不编码，也不要自动增加我没有提出的栏目。
```

### 3.1 气质关键词

我把视觉方向整理成几个词，方便以后新增页面时继续沿用：

- **安静的编辑感：** 通过标题、图片大小和留白安排阅读节奏，减少抢注意力的装饰。
- **暖灰色：** 浅色背景、深色标题和较柔和的正文颜色，形成清楚的层次。
- **衬线标题：** 标题带有书刊感，正文使用清晰的无衬线字体。
- **克制的小标签：** 分类、日期和区块名称保持较小的字号，与主内容区分。

这些词要能在页面上看见。比如“克制”可以具体表现为：减少按钮数量、保持分隔线轻薄、不让每个区块都出现复杂动效。

### 3.2 字体

本站正文使用 Geist Sans，标题使用衬线字体。它们分别承担长文阅读与视觉定位的作用。

选字体时，我会把真实的中英文标题、段落和日期都放进去看。单个英文词好看，不代表长标题和中文段落也合适；手机上的字号、行距和换行同样需要检查。

### 3.3 色彩与组件模式

确定大方向后，还要统一重复出现的元素。这样新增页面时，AI 就有明确依据。

| 元素 | 本站的处理方式 |
| --- | --- |
| 页面背景与文字 | 暖灰背景，深色标题，正文与辅助信息分层 |
| 区块与卡片 | 使用细边框、适度圆角和较浅底色，避免层层套框 |
| 分类与链接 | 使用清楚的文字、细分隔线和统一的悬停反馈 |
| 后台 | 沿用相近色系，优先保证导航、表单和保存操作清楚 |

我会把这些规则保存在项目说明里，让 AI 修改前先读。反馈也尽量具体，例如：“项目标题被分类标签抢了注意力，请突出标题，保留现在的颜色和间距。”这样比反复要求“再高级一点”更容易得到稳定的结果。

## 内容与媒体：怎么处理、怎么呈现

作品集不只是文字，还有高清照片和长视频。它们需要不同的阅读与管理方式。我会先判断材料怎样展示，再考虑它们保存在哪里。

最初，文字记录与图片都主要交给 Supabase。随着图片和大文件增多，免费存储空间与访问流量额度都不够用，新内容也无法顺利上传。我把图片和其他大文件转到 Cloudflare R2，Supabase 继续保存文章、作品资料、登录信息和文件地址。

R2 是保存文件的对象存储服务。对网站来说，可以理解为：文件放在那里，内容通过地址引用它。

| 内容 | 怎样管理 | 怎样展示 |
| --- | --- | --- |
| 文章与项目文字 | 后台编辑，保存在 Supabase | 文章、项目介绍和目录 |
| 照片与附件 | 文件主要放在 R2，Supabase 保存地址和说明 | 首页封面、图库、图片或下载入口 |
| 视频 | 保留已有 Google Drive 链接；按需要使用文件存储 | 在项目或旅途记录中播放 |
| 图文混合记录 | 按内容安排文字、图片与视频 | 连续叙事或图库，取决于材料 |

这个安排是在使用中逐渐调整的。刚开始材料少时，可以先用简单方案；当空间、流量或上传成为实际问题，再比较扩容和迁移。选择服务时也要考虑以后怎样管理、怎样备份，不能只看第一次接入是否方便。

## 技术栈选型与理由

### 5.1 先做出能展示的版本

刚开始做网站时，我并不了解前端、后端和数据库各自是什么，也没有先选好一整套技术方案。我的目标很直接：尽快做出一版可以展示作品、让别人了解我的网站。

这个阶段，我先整理个人介绍、代表作品和参考网站，再借助 AI 把它们做成可以预览的页面。文字和图片先直接放在项目文件里，修改后再发布。这就是我起步时的静态展示方式，暂时不需要内容管理后台。

有了实际页面，才容易判断效果：首页的顺序是否合适，图片和文字的比例是否舒服，点击后能否看到完整作品，手机上是否好读。这些反馈帮助我明确下一步要改什么。

如果你也从零开始，可以先让 AI 做一个范围较小、内容真实的版本：一段个人介绍、几个代表作品，以及必要的联系入口。等这一版能够清楚表达自己，再根据使用中遇到的问题增加功能。

### 5.2 更新变多后，再加入后台

静态展示能满足起步时的需要。但作品和内容逐渐增加后，每次改文案、换图片都要打开项目文件，再发布一次，维护就变得麻烦了。我开始需要一个登录后就能编辑内容的管理页面，也就是前面提到的 CMS。

我最早从 Projects 开始：先让已有项目能在后台修改，再让公开页面显示更新后的内容。确认这套方式可用后，才逐步扩展到其他栏目。

也是在解决这些问题的过程中，我才逐渐理解几个概念：**前端**是浏览和操作的界面；**后端**负责处理保存、检查权限等请求；**数据库**则保存项目名称、介绍、分类等有组织的资料。做展示页时，先有能看的页面就可以；需要登录编辑、长期保存修改时，才需要进一步考虑这些部分怎样配合。

本站用 Supabase 保存内容和处理登录，再通过自己网站里的管理页面完成编辑。这样，我可以在浏览器里修改项目、调整排序，更新后的内容由公开页面读取，不必每次都去改代码。

现在回头看，选工具时更值得问的是：**它解决了我当前哪个问题，以后我能不能继续维护？** 如果只是偶尔更新几个作品，静态页面仍然可以使用；当更新频率提高，再增加后台也来得及。

### 5.3 现在使用的工具

技术栈就是支撑网站的一组工具。下面是网站发展到现在使用的主要工具，不是第一版就需要准备齐全的清单：

| 工具 | 在本站负责什么 |
| --- | --- |
| **Next.js** | 组织页面、读取内容，并处理后台的保存等操作 |
| **React** | 将导航、项目列表、图库等界面拆成可重复使用的部分 |
| **TypeScript** | 帮助检查数据类型，减少部分代码错误 |
| **Tailwind CSS** | 编写和统一页面样式 |
| **Supabase** | 保存文章、项目资料等内容，处理登录和访问权限 |
| **Cloudflare R2** | 保存图片与其他大文件 |
| **Vercel** | 构建并发布网站，提供正式与预览地址 |
| **Markdown 编辑与展示工具** | 支持文章的编辑、排版和阅读 |

网站要让别人访问，还需要发布到线上。这个作品集使用 Vercel，主要因为它能连接代码仓库，自动构建和发布，减少自己维护服务器的工作。我也写过另一种方案——[阿里云 ECS Docker 部署教程](/notes/aliyun-ecs-docker-deploy)，可以按自己的维护意愿选择。

前面提到的 R2，则是图片和大文件增长后才加入的。它解决存储空间与流量压力，Supabase 继续保存内容资料和文件地址。这也是同一个过程：先遇到具体问题，再调整相应的工具。

选择这些服务之后，仍然要管理账号、域名、用量和续费。可以让 AI 结合当前需求解释候选方案：为什么需要、更新时怎么操作，以及会多出哪些维护工作，再决定是否接入。

## 内容管理：数据库与后台

### 6.1 先确定要管理什么

有了后台之后，平时更新网站就不必去修改项目文件。对我来说，Supabase 负责保存内容和处理登录，网站里的管理页面则提供日常编辑的入口。

接入前，我需要先说明想怎样管理内容。例如，一个项目除了名称与介绍，还要有封面、图库、分类和发布状态；图库里的照片属于哪个项目、怎样排序，也要一起保存。把这些关系告诉 AI，它才能安排对应的资料和编辑功能。

不必先学会设计整套数据库。可以先描述一次真实操作：“我想新增一个项目，上传几张图片、调整顺序，先保存为草稿，确认后再公开。”让 AI 根据这条流程解释需要保存什么，再做出可以实际使用的后台。

### 6.2 把日常编辑做顺手

我从 `/admin/login` 登录，进入后台后通过侧栏切换模块。电脑上可以折叠侧栏，手机上使用菜单，保持编辑区有足够空间。现在主要在这里完成这些工作：

| 模块 | 管理的内容 | 日常操作 |
| --- | --- | --- |
| Site Settings | 首页文案、主视觉和展示图片 | 修改介绍、更换选图 |
| Projects | 项目介绍、分类、图片、视频和展示方式 | 新增或更新项目、调整图库与排序 |
| Traces | 摄影、绘画合集与旅途记录 | 添加作品、补充说明、调整排列 |
| Notes | 双语标题、摘要、正文和附件 | 编辑文章、保存草稿或发布 |
| Workbench | 工作阶段、相关文章和资源 | 整理流程、更新文章与资源入口 |
| About | 个人介绍、经历、关注领域和照片 | 更新背景资料 |
| Guestbook | 留言、联系信息与审核状态 | 查看、通过、拒绝或删除留言 |
| Analytics | 内容访问记录 | 按不同时间范围查看统计 |

后台功能也是随实际需要补齐的。例如，首页展示图后来有了独立设置，换首页选图时，不必同时修改项目详情中的原图。与 AI 讨论这类需求时，要说明自己想单独调整什么、哪些地方应该继续共用。

后台是否好用，主要看能否找到要改的内容，保存和发布是否清楚，失败时是否有提示。每次增加编辑功能，我都会亲自改一条内容，再打开公开页面核对文字、图片和顺序；重新进入后台后，也要能继续编辑。双语内容更新时，两种语言一起核对。

### 6.3 谁能看，谁能改

后台供自己使用，网站则让访客公开浏览，两边能看到和操作的内容需要分清楚。我会先向 AI 说明这些要求，再让它在数据库和保存操作中设置相应的访问规则：

- **普通访客：** 可以阅读公开内容，看不到草稿和后台资料。
- **网站管理员：** 登录并通过权限检查后，可以编辑内容和查看管理信息。
- **访客提交：** 留言先进入待审核状态；邮箱等联系信息只供管理使用。

留言功能还需要持续查看和处理。是否加入，可以根据自己想不想经营这种交流方式决定。

权限需要实际验证。用未登录浏览器检查公开内容，再确认草稿、管理操作和私有资料没有被公开。不能仅因为页面上藏了按钮，就认为访问已经受到限制。

### 6.4 维护文件与旧链接

网站从本地素材发展到在线管理，再从 Supabase 调整到 R2，都涉及已有文件和链接。迁移的难点是让原来的内容继续可用。

我的处理顺序是：

1. **清点：** 找出需要搬运的文件，以及哪些页面引用了它们。
2. **复制：** 先把文件放到新位置，保留原文件。
3. **核对：** 检查文件是否完整、新地址是否可以访问。
4. **切换：** 更新内容中的引用，逐页查看展示结果，并测试新文件上传。

早期也遇过本地只下载了部分仓库、缺少原图的情况，需要先补齐材料才能导入。让 AI 执行迁移前，应先说明哪些是已有正式内容、哪些只是本地文件，并保留可恢复的副本。

迁移完成后，日常更新继续走后台。历史上的批量导入脚本不等于普通上传操作，不应为了检查网站而重复运行。

调整栏目入口时，我也保留了原来的摄影和绘画网址。这样，过去分享出去的链接仍能打开对应内容。维护网站不仅是添加新材料，也要检查已有图片和链接是否继续可用。

## 部署、域名与环境变量

下面三部分按上线后的需要展开：先让网站能访问，再完善搜索展示，最后了解使用情况。这些工作可以逐步完成。

### 7.1 部署流程

本地预览用来自己检查页面，部署则把网站发布到网上，让别人通过网址访问。

本站将 Vercel 连接到代码仓库。正式代码更新后，平台会构建并发布；其他分支可以生成预览地址，先检查再决定是否用于正式网站。

可以按这个顺序与 AI 配合：

```text
本地修改与预览 → 运行代码检查 → 查看预览版本 → 确认后发布 → 打开正式网址核对
```

“代码已提交”和“网站已上线”是两件事。发布失败时要查看原因；发布成功后，也要实际访问。只通过后台改文章，通常不必重新发布整套网站代码。

### 7.2 域名配置

域名就是访客记住和访问网站的地址。可以先用托管平台提供的网址，确认主要页面正常后，再绑定自己的域名。

| 域名 | 本站用途 |
| --- | --- |
| `www.qiannawang.com` | 正式主站 |
| `qiannawang.com` | 跳转到主站，保持入口一致 |
| `qianna-site.vercel.app` | 平台提供的备用地址 |
| `media.qiannawang.com` | 公开媒体文件的访问地址 |

配置时，需要在托管平台绑定域名，并在域名服务中填写相应解析记录。可以让 AI 解释每一步，再检查带与不带 `www` 的入口、HTTPS 和页面链接是否正常。

### 7.3 环境变量

环境变量保存网站运行时需要的配置，例如连接哪个数据库、使用哪个文件存储、正式网址是什么。本地电脑与线上平台分别配置，不能假定本地能运行，线上就已经准备好。

可以让 AI 整理一份说明：每项配置去哪里获取、填在哪里、是否属于私密信息，以及更改后是否需要重新发布。

账号密码、存储密钥等私密信息不能出现在公开页面或代码仓库中。配置问题尽量在对应平台中处理，不要为了排错把完整密钥放到截图或公开说明里。

### 7.4 登录邮件的返回地址

Supabase 发送登录确认或密码重置邮件时，需要知道用户点击后应返回哪个网站。如果还保留旧域名或本地地址，邮件就可能把人带错地方。

因此，绑定正式域名后，还要核对登录服务中的网站地址和允许返回的地址。然后亲自发送一封邮件，点开链接，走完返回与登录流程。预览版本若需要使用登录，也要单独检查。

## SEO 与 GEO 优化

### 8.1 问题背景

我曾收到一条 SEO 推销留言，随后自查发现，网站的页面信息还留着默认的 `Create Next App` 标题。这才意识到：页面能打开，也要继续检查它在浏览器标签、分享预览和搜索结果里怎样介绍自己。

SEO 是帮助搜索引擎发现和理解网页的工作。我先补齐基础信息，再看搜索平台实际收录了哪些页面。

### 8.2 已实施 SEO

| 项目 | 解决什么问题 |
| --- | --- |
| 网站与页面标题、简介 | 说明当前页面是什么，避免保留默认模板文字 |
| 分享预览信息 | 分享链接时，显示合适的标题、简介和封面 |
| 统一正式网址 | 减少带与不带 `www` 等不同入口造成的混乱 |
| 站点地图 | 列出公开页面，帮助搜索引擎发现内容 |
| 抓取说明 | 告诉爬虫哪些地方不适合抓取；后台仍靠登录与权限保护 |
| 作者与网站资料 | 用统一格式说明网站、作者及其关联信息 |

这些设置可以交给 AI 协助完成，但需要提供准确的姓名、简介、领域和正式网址。项目与文章更新后，也应检查它们的标题和摘要是否仍然合适。

### 8.3 GEO（生成式引擎优化）

GEO 通常用来讨论怎样让内容更容易被生成式搜索和 AI 回答理解、引用。我在本站的做法，首先还是把内容写清楚。

1. About 开头说明自己的身份与关注领域。
2. 用网站和作者的结构化资料补充一致的信息。
3. 每篇文章和项目有可以独立理解的介绍，说明主题与成果。
4. 提供 `llms.txt`，用文本介绍网站内容与入口。

例如，读者只看到项目开头的一段，也应知道它研究什么、我做了什么。这些工作有助于表达准确，但不能保证某个 AI 平台一定读取、收录或引用网站。

### 8.4 部署后操作

我的检查顺序是：

1. 在正式网址核对标题、简介、封面和页面链接。
2. 在 [Google Search Console](https://search.google.com/search-console) 验证自己管理这个网站。
3. 提交站点地图 `sitemap.xml`，查看处理结果。
4. 用网址检查功能了解重要页面的抓取与收录状态。

本站已完成域名验证与站点地图提交，也确认过首页收录。后续新增页面仍需要继续查看；刚发布就搜不到，不一定是故障。

对个人作品集，我会先把基础信息、个人介绍和内容本身做好。是否需要进一步优化，再根据实际用途和搜索表现判断。

## 访客分析与数据管理

### 9.1 两套分析互补

我既想了解整个网站的访问，也想知道具体文章和项目的情况，因此保留了网站自己的记录和平台工具：

| 来源 | 主要看什么 | 入口 |
| --- | --- | --- |
| 网站自己的访问记录 | 哪些内容被打开、访问次数和大致停留时间 | 后台 Analytics |
| Vercel Analytics | 整体流量趋势与来源 | Vercel 管理页面 |
| Speed Insights | 加载、操作响应和页面是否容易出现位置跳动 | 平台的体验统计 |

浏览次数通常叫 PV，独立访客数通常叫 UV。后者依赖统计方式，同一个人换浏览器也可能被重新计算；看趋势时要记住这些限制。

### 9.2 怎样使用访问记录

后台可以按不同时间范围查看内容访问。它能帮助我发现哪些项目或文章经常被打开，再结合网站目标判断是否值得补充说明、更新材料或增加入口。

打开页面不代表读完，停留时间也可能受到离开标签页等行为影响。访问量少时尤其不必急着给内容排名，可以先找几位读者实际试用，了解他们怎样浏览。

例如，想让别人通过项目了解自己的工作，就可以请对方看完后说说：记住了哪个项目，是否理解我的贡献，下一步入口是否清楚。这样的反馈比单个数字更容易转化为修改。

### 9.3 Guestbook 作为“软信号”

留言能补充统计无法说明的信息：读者对哪里感兴趣、哪段没看懂、有没有实际交流的需要。真实反馈值得回应，也可以成为下一次整理内容的依据。

我仍保留先审后发。泛泛的推销和垃圾留言可以拒绝公开，不需要因为它们出现，就判断自己的网站必须增加某项服务。

## 附录：建站过程里的一些心得

记录我在从零搭作品集时的工作方式与判断，供做类似网站时参考。

### 先定气质和内容，再选框架

我有意把内容与视觉相关的章节放在前面。开始时最想清楚的是两件事：**首页按什么顺序阅读，以及整站要安静还是热闹。**

想明白这些之后，才容易判断一个版式、交互或工具是否适合自己。技术可以调整，但作品和个人表达需要有自己的依据。我的暖灰色系、衬线标题与克制交互，也是在这样的判断中慢慢确定的。

### 小步迭代

Projects、Traces、Notes、Guestbook 和 Analytics 都是陆续加入的，Workbench 也是在文章与资源逐渐增加后才出现。

每次我会先把一种内容的流程走通：准备材料，安排展示，完成编辑，再试一次更新。确认能使用后，再扩展到下一类内容。这样既能沿用已经合适的模式，也能及时发现不值得继续做的部分。

我更在意每次增加的功能是否解决了实际问题。例如，后台让更新方便起来，R2 解决文件增长后的存储压力；这些需要都是在使用中逐渐明确的。

### 与 AI 协作建站的真实感受

本站不少功能是在 Cursor 里与 Agent 一起完成的。Agent 可以理解为能读取项目、修改文件并运行检查的 AI 助手。它帮助我推进实现，但内容、风格与取舍仍需要我持续参与。

几条对我有用的习惯：

- **一次给一个具体目标。** 例如“首页项目介绍太长，请保留名称、封面和一句简介，让人能点进详情”，比“全面优化首页”更容易检查结果。
- **先读现有实现。** 要求 AI 参考已有页面、字体和导航规则，再做修改，减少每轮风格都变化的问题。
- **看真实页面。** 描述当前现象、带来的影响和希望的结果，必要时附截图，圈出需要调整的位置。
- **检查之后再保留。** 让 AI 做代码检查与构建，再自己试菜单、详情、手机浏览和后台更新。它报告完成后，仍要确认实际结果。

可以这样给一轮反馈：

```prompt
这次只调整【页面或板块】。
当前问题：【看到的现象，以及为什么影响阅读或操作】。
希望结果：【可以在页面上确认的变化】。
参考：【截图，或网站中已经合适的页面】。

请先阅读现有实现，说明准备怎样改。
沿用现有视觉规则，保留未涉及的内容和功能。
修改前保留可恢复的版本，完成后检查电脑和手机上的实际效果，
并告诉我检查了什么、还有什么需要我亲自确认。
```

此外，我会让 AI 根据项目实际使用的版本查文档。工具和框架会变化，旧教程里的做法未必适用于当前项目。

### 善用 MCP：把 Supabase、GitHub、Vercel 接进 Cursor

只读本地文件，AI 不一定知道线上数据库是什么状态、发布有没有成功。MCP 是一种让 AI 工具连接外部服务的方式，在授权范围内帮助它查询真实情况，减少来回复制截图和错误信息。

按本站的服务组合，我主要用这些连接：

| 服务 | 可以帮助检查什么 | 建站时的场景 |
| --- | --- | --- |
| **Supabase** | 内容结构、访问规则与运行日志 | 后台保存失败时，查原因；新增内容前，先确认已有结构 |
| **GitHub** | 代码版本、修改记录和自动检查 | 核对修改是否已保存，查看提交后的检查结果 |
| **Vercel** | 发布状态、域名、运行设置和错误日志 | 确认正式版本是否更新，排查发布失败或域名问题 |

几个实用习惯：

1. **需要时先查真实状态。** 比如新增内容类型前，先检查现有资料怎样组织，避免凭旧描述猜测。
2. **重要操作先了解影响。** 删除正式内容、修改线上配置或扩大权限时，我会先看操作范围、是否能恢复，再决定执行。
3. **区分查询和批量处理。** 工具连接适合查状态、对配置、排问题；批量搬文件等工作仍要有清单和核对过程。
4. **文档另外核查。** 官方文档或 Context7 等文档工具，用来确认具体做法；线上工具则用来检查实际状态。

接入时，在 AI 工具的连接设置中添加需要的服务，确认权限并完成授权。具体入口随工具版本变化，按当前说明操作。连接失败或授权到期时，需要先恢复连接，不能把 AI 的猜测当作查到的结果。

### 个人网站当实验室：首页涟漪例子

作品集也适合放一些想试的小交互。我曾给首页封面做过水面涟漪：鼠标移动或点击时，图片出现轻微扭曲。

为了试效果，我还做了只在开发时出现的调节面板，用滑条调整波速、折射程度和拖尾，再把满意的设置保存下来。减少动态效果的系统偏好也需要照顾，不能要求所有读者都观看动画。

**目前这项涟漪效果已经关闭。** 我保留了实验代码，首页使用更轻的动效。它带来的经验仍然有用：可以先把效果单独做出来，亲自感受，再决定要不要留在正式页面。

以后想试新的图库浏览方式、滚动效果或文章展示，也可以用类似方法。个人网站给了我试验空间，而是否保留，最终回到内容和浏览体验。

### 给自己留一点过程记录

我会给较大的修改留一份简短记录，说明为什么改、选了什么办法、怎样检查，以及出问题时怎样恢复。几个月后重新打开项目，这些记录比只看最后的页面更容易接上思路。

日常维护还要能找到原始图片、文字、账号归属、服务用量和续费信息。对外分享放在 Notes，自己维护需要的细节则留在项目文档里。

### 给想动手读者的最小启动建议

如果你准备做个人网站，可以参考我当时的顺序：

1. **先做静态预览。** 准备个人介绍、少量代表内容与参考图，用 AI 帮忙确定页面顺序和气质。
2. **让一条浏览路径完整。** 从首页进入项目或文章，再返回列表或找到联系方式，用电脑和手机都试一次。
3. **按更新需要增加后台。** 选最经常修改的一类内容先做，我最早从 Projects 开始。
4. **上线后补齐基础信息。** 核对正式网址、标题、简介、图片和分享效果，再按需要增加搜索与访问分析。

这只是我的路径。材料和更新节奏不同，第一版的范围也可以不同；有一页能清楚表达自己，同样可以开始。

## 经验总结与后续方向

### 11.1 后来证明好用的选择

1. **让内容容易更新。** 把经常修改的内容交给后台，降低持续使用的阻力；更新不频繁的部分保持简单。
2. **沿用已经合适的模式。** 新增栏目时参考已有的阅读和编辑流程，少一些重复决定。
3. **保持视觉一致。** 字体、颜色、间距和链接方式有共同规则，页面扩展时仍然像同一个网站。
4. **先审核再公开留言。** 保留交流入口，也保留自己管理公开内容的能力。
5. **上线后继续检查。** 页面、搜索展示、分享预览和后台更新，都需要实际使用来确认。

### 11.2 踩坑清单

| 现象 | 我会先检查什么 | 对建站过程的提醒 |
| --- | --- | --- |
| 本地图片空白 | 素材是否下载完整，文件地址是否正确 | 先确认输入材料，再修改展示代码 |
| 图片越来越多，上传受限 | 存储空间、流量和上传方式 | 按实际用量调整服务，迁移前保留原文件 |
| 登录邮件跳错页面 | 登录服务配置的返回地址 | 正式域名改完，也要走一次邮件流程 |
| 本地可预览，发布却失败 | 构建错误与所用版本的文档 | 让 AI 根据具体错误检查，不能只看预览 |
| 详情页报错 | 页面需要的数据和读取方式 | 新功能要实际点开，不能只检查首页 |
| 标题还显示默认文字 | 页面标题、简介和正式网址 | 上线时连浏览器标签和分享预览一起看 |

### 11.3 可选后续

后面继续根据内容和使用需要调整：

- 查看 Search Console 的收录情况，处理重要页面的问题。
- 完善 Notes 的封面和配图展示。
- 补充 LinkedIn 等公开身份入口，方便了解背景和联系。
- 为需要不同叙事的项目增加展示模板。
- 按阅读需求增加 RSS 订阅，让关注文章的人能接收更新。

这些是候选方向。哪一项先做，取决于它是否解决了当前使用中的问题。
