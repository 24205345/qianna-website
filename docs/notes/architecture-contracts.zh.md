# 【AI 开发工作流 · 03】 架构与接口契约：从产品需求到可验证的技术决定

> **阅读背景**
> [产品定义](https://www.qiannawang.com/notes/scope-product-definition)明确了服务谁、完成什么任务和如何验收。接下来，需要把这些决定转化为系统职责、数据流和交互约定，使界面设计、开发与验证能够使用同一份依据。

这一阶段回答：**谁负责，各部分如何协作，失败后怎样继续？** 保存结构、核心流程、契约和重要决定的理由即可。

把 AI 方案视为候选。选型应适配产品需求、现有能力、运行限制和维护成本；影响方向的判断需核对对应版本官方资料，再做小范围试验。

按“约束 → 选型 → 职责 → 契约 → 验证与交接”阅读，提示词随使用环节放置。

---

## 1. 从产品定义提取技术约束

### 找出会改变方案的条件

从 PRD 的核心流程、验收标准和已知约束开始。把“希望好用”转成会影响实现的条件，区分业务要求、暂定目标和实际测量结果。

| 产品中的条件 | 架构需要回答的问题 | 确认方式 |
| :--- | :--- | :--- |
| 用户输入文本、文件或媒体 | 谁获取和解析输入，允许多大，哪些内容可以发给外部服务 | 代表性输入和数据使用要求 |
| 用户等待处理结果 | 同步返回是否可行，是否需要任务查询或流式反馈 | 等待目标、实际耗时和宿主运行限制 |
| 需要下次继续或跨设备访问 | 哪些状态必须保存，保存多久，怎样识别使用者 | 具体恢复场景和权限要求 |
| 多人操作或涉及收费 | 谁可以访问资源，重复请求会不会产生重复操作或费用 | 权限规则与重复操作样例 |
| 依赖外部接口 | 配额、失败、成本和数据处理条件是否影响流程 | 对应版本文档与小范围调用 |

例如，上一章的知识问答工具只验证单次练习。题目和作答可以先保留在当前页面，服务端负责生成与校验；是否需要历史记录另有依据。若任务需要跨次复习，就应重新讨论持久化。没有历史功能，也仍要说明临时状态、运行日志和外部服务如何处理材料。

### 优先验证影响方向的不确定性

分开记录已确认条件、暂定目标与未知项。先验证输入可获取性、关键平台能力和运行限制，再细化目录与命名。

用一份代表性输入记录耗时、成本和失败行为；未经测量的指标仍是目标。

## 2. 根据约束比较架构与技术栈

先把产品约束、可行候选和验证依据放到同一条决策流程中。下图概括选型步骤，后面再展开技术栈比较与核查案例。

[![把 AI 建议变成有依据的决定 — 影响方向的假设未核实前，推荐方案仍是候选。](https://media.qiannawang.com/notes/workbench-diagrams/v3/architecture-decisions.zh-1cc714ee509b.webp)](https://media.qiannawang.com/notes/workbench-diagrams/v3/architecture-decisions.zh-1cc714ee509b.webp)

*影响方向的假设未核实前，推荐方案仍是候选。 [查看原图](https://media.qiannawang.com/notes/workbench-diagrams/v3/architecture-decisions.zh-1cc714ee509b.webp)*

### 先区分系统结构与工具名称

客户端框架、服务端框架、数据库、托管服务和编辑器解决不同问题，可以组合使用。Taro 与 uni-app 主要影响客户端；FastAPI 与 NestJS 主要用于服务端；VS Code 与 HBuilderX 影响开发工作流。选定客户端框架，不会自动决定后端语言。

先决定哪些职责共用应用、哪些需独立运行、哪些适合托管。已有行为和兼容要求优先；每增加一个服务，都要说明收益和运维成本。

### 常见候选及适用场景

下表是帮助比较的组合示例。产品场景、团队经验和关键能力验证会影响最终选择，表格不构成固定推荐顺序。

| 场景 | 候选组合 | 示例与主要核查点 |
| :--- | :--- | :--- |
| 网站、内容平台、轻量 Web 产品 | Next.js + TypeScript，按需组合数据库和托管能力 | 作品集、会员内容网站、预约工具；检查页面呈现、服务端职责与运行限制。[Next.js 文档](https://nextjs.org/docs) |
| 已有前端，需要独立业务服务 | React / Vue + NestJS | 管理后台、多个客户端共享业务接口；确认独立服务的收益和维护成本。[NestJS 文档](https://docs.nestjs.com/) |
| 核心处理依赖 Python | Web 客户端 + FastAPI | 文档处理、数据分析、模型服务；检查 Python 依赖、耗时与资源需求。[FastAPI 文档](https://fastapi.tiangolo.com/) |
| 明确服务微信单端 | 微信原生小程序 | 门店服务或微信内业务流程；核查平台能力、发布要求和实际跨端需求 |
| 希望沿用 React / Vue 经验进行跨端开发 | Taro + 按业务选择的服务端 | 小程序优先、逐步扩展客户端；核查目标版本、组件库与目标端的支持组合。[Taro 官方仓库](https://github.com/NervJS/taro) |
| 希望沿用 Vue 进行跨端业务开发 | uni-app + 按业务选择的服务端 | 表单、内容、预约类产品；核查编译方式、插件与各端运行调试流程。[uni-app 文档](https://uniapp.dcloud.net.cn/quickstart-cli.html) |

已有 Java、.NET 或其他成熟系统时，也应将沿用现有能力列入候选。数据库、队列和缓存根据数据保存、一致性、任务执行等要求加入；调用 AI 接口本身并不要求使用 Python，也不自动要求增加独立后端。

### 案例：核查 AI 对小程序工具链的建议

假设项目先做微信小程序，可能扩展 H5，希望继续使用 VS Code。AI 初步推荐 uni-app 后，开发者追问：“哪些环节能用现有编辑器和 CLI，哪些必须使用专用工具？”

核查时，把编辑、编译、运行调试和打包发布分别确认。uni-app 官方说明 CLI 项目可以使用 VS Code 等编辑器；App 的运行调试仍有 HBuilderX 工具要求。小程序、H5 与 App 的流程应分别核对，uni-app 与 uni-app x 也应分开检查。[官方 CLI 与工具说明](https://uniapp.dcloud.net.cn/quickstart-cli.html)

接着用候选方案跑通一个页面、一种关键平台能力和一次真实接口调用，记录所需工具和适配工作。若开发者更熟悉 React，且 Taro 的目标端验证通过，可以有依据地选择 Taro；已有 Vue 和 uni-app 经验时，结论可能不同。这是条件化的判断示例，并非已完成的项目测试结果。跨端支持仍需要平台适配与真机验证。

### 用 AI 比较方案并指出证据缺口

```prompt
请根据产品定义比较当前阶段需要的架构与技术栈。

产品定义与核心流程：【粘贴 PRD 或摘要】
目标平台与首发范围：【Web、小程序、App 或其他】
已有项目与技术经验：【现有代码、熟悉的语言和工具】
约束与已测结果：【时间、预算、数据、耗时、部署条件】
需要核实的问题：【列出关键不确定性】

请完成：
1. 提取影响架构的条件，区分已确认要求、暂定目标和待验证假设。
2. 比较最多 3 个可行方案，包括适用的现有能力；分别说明满足哪些需求、引入什么开发与维护成本、何时不适合采用。
3. 区分客户端、服务端、存储、托管能力和开发工具，说明各自职责及组合关系。
4. 对版本兼容、平台能力和工具链限制提供官方来源与核对日期；未知内容明确标记，不要假装做过验证。
5. 为最影响方向的风险提出最小试验，说明输入、观察项和如何根据结果决定。
6. 给出有适用条件的建议及重新考虑的条件，不要只列技术名称。

允许质疑最初的推荐。优先适配产品需求和现有能力，不默认前后端分离、微服务、特定框架或数据库。
缺少会改变方向的条件时，先提出最多 5 个关键问题，等待回答后再确定相关结论。
当前先形成架构草案，不直接生成完整项目或开始大规模改造。
```

### 从一次操作走到可观察结果


沿流程追踪输入、状态、结果和失败入口，分清界面状态与服务端需保存的状态。

## 4. 把交互写成明确契约

### 约定结构、含义与行为

契约是协作双方共同遵守的输入、输出和行为约定。HTTP API 可以使用 [OpenAPI](https://learn.openapis.org/specification/structure.html) 描述；应用内部函数可以使用类型和运行时校验，事件也需要说明消息结构与处理规则。语言中的类型声明还需要与实际传入数据的校验配合。

一段成功 JSON 只是样例。完整契约还应写清：

- 触发方式、调用方、权限和适用版本。
- 字段类型、必填项、是否允许空值、单位、长度与枚举。
- 正常结果、失败结构、等待预算和重试行为。
- 重复请求、状态变化、兼容要求和代表性样例。

### 示例：单次练习的同步契约

以下延续单次练习范围，假设技术试验允许同步返回。数字和超时预算均为示例决定，未作为实测能力；若宿主限制或试验不支持，应调整方案。

| 项目 | 示例约定 |
| :--- | :--- |
| 操作 | `POST /api/practice-sessions`，JSON 请求体包含必填字符串 `material` |
| 输入边界 | 去除首尾空白后按 Unicode 码点计数，接受 200–2,000 个字符；服务端再次校验 |
| 成功结果 | HTTP 200，返回包含 `questions` 的对象，数组恰好 3 项；每题 ID 在本轮唯一 |
| 题目结构 | 题干、4 个带唯一 ID 的选项、1 个有效的正确选项 ID、解析和原文片段；这些字段均必填且不允许为空 |
| 输出约束 | 正确选项必须属于本题选项；解析和答案应能由原文支持，结构校验之外另做内容检查 |
| 等待与重试 | 示例服务端外部调用预算为 20 秒，上线前核对宿主限制；处理中阻止界面重复提交，失败后允许显式重试 |
| 保留边界 | 本轮题目和作答保留在当前页面；关闭后不承诺恢复；重试可能重新生成并产生额外调用成本 |

`questions` 与 `choices` 是数组，题目和选项是对象。题目的 `id`、`prompt`、`correctChoiceId`、`explanation`、`sourceQuote` 及选项的 `id`、`text` 均为非空字符串。

下面仅展示一个题目对象，完整成功响应仍应有 3 道题。原文片段“活动于每周三晚上七点开始”提供了本题答案的依据。

```json
{
  "id": "q1",
  "prompt": "活动在星期几举行？",
  "choices": [
    { "id": "a", "text": "星期二" },
    { "id": "b", "text": "星期三" },
    { "id": "c", "text": "星期四" },
    { "id": "d", "text": "星期五" }
  ],
  "correctChoiceId": "b",
  "explanation": "原文明确说明活动于每周三举行。",
  "sourceQuote": "活动于每周三晚上七点开始。"
}
```

这个示例是个人自测，允许客户端拿到答案并展示反馈。正式测评或答案需要保密时，应重新设计答案返回和服务端评分边界。材料不足以生成约定题目时，返回可识别的失败，不能为了凑足数量编造内容。

### 用 AI 起草契约

```prompt
请根据已选择的方案，为核心流程起草可执行的交互契约。

产品定义与验收：【粘贴】
架构职责与核心流程：【粘贴】
已确认的技术方案与约束：【填写】
需要协作的边界：【HTTP API、函数、事件或任务】

请输出：
1. 每项交互的调用方、触发条件、输入输出、字段类型、必填与空值规则、单位及合法状态。
2. 正常、边界和失败样例，约定错误码、对用户的含义、等待预算与重试行为。
3. 身份和资源权限校验位置、重复操作语义，以及需要保留哪些状态。
4. 与所选边界匹配的契约草案，例如 OpenAPI、类型定义或事件 Schema，并说明校验方式。
5. 需要从样例进一步确认的含义、兼容要求和未解决问题。

契约必须对应本期需求，不擅自增加账户、支付、队列或持久化。
结构有效与业务正确分别检查；不要把一个成功样例当成完整 Schema。
对会改变核心行为的缺口先提出关键问题，其余注明假设。
保持正常结果、错误样例、Mock 和验收标准一致，暂不实现业务代码。
```

## 5. 约定权限与失败行为

### 明确可信边界

把“识别调用者”和“允许访问某项资源”分别说明。涉及用户资源时，在可信服务端逐次校验访问权限；客户端显示或隐藏按钮只是交互安排。匿名功能也需要明确可调用范围和资源消耗控制。

模型密钥、受保护的业务凭据和收费决定留在可信服务端。客户端输入及外部生成结果均需校验；文档还应说明材料会传给哪些服务，以及日志和数据保留边界。浏览器跨域场景按实际来源配置 CORS，它不承担身份或资源权限校验。可参考 [OWASP REST 安全说明](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html)。

### 将失败变成稳定的交互结果

沿用前文的单次练习同步调用，先看成功与失败如何分别返回客户端，再据此约定下面的错误编码和恢复行为。

[![契约也要包含失败后的交互 — 同步示例：超时结束本次等待，并不代表上游任务已取消。](https://media.qiannawang.com/notes/workbench-diagrams/v3/architecture-failures.zh-8e8988b9d1d1.webp)](https://media.qiannawang.com/notes/workbench-diagrams/v3/architecture-failures.zh-8e8988b9d1d1.webp)

*同步示例：超时结束本次等待，并不代表上游任务已取消。 [查看原图](https://media.qiannawang.com/notes/workbench-diagrams/v3/architecture-failures.zh-8e8988b9d1d1.webp)*

以下是练习示例可采用的错误约定，具体编码需要在项目中统一定义。

| 情况 | HTTP 与应用错误码示例 | 调用方应如何处理 |
| :--- | :--- | :--- |
| 输入类型或长度不符合要求 | 400 / `INVALID_INPUT` | 保留材料并提示修改 |
| 材料不足以生成题目 | 422 / `INSUFFICIENT_MATERIAL` | 说明原因并允许补充材料 |
| 达到调用限制 | 429 / `RATE_LIMITED` | 告知稍后重试，遵循服务端返回的等待信息 |
| 上游失败或输出不符合契约 | 502 / `UPSTREAM_FAILURE` 或 `INVALID_OUTPUT` | 保留输入，按错误含义提供显式重试 |
| 生成超过约定等待预算 | 504 / `GENERATION_TIMEOUT` | 结束当前等待并提示重试，不假定上游工作已经取消 |

失败响应可以统一包含 `error.code`、可展示的 `error.message`、`error.retryable` 和用于排查的 `requestId`。不返回密钥、原始调用栈或内部服务详情。对超出应用控制范围的断网和宿主失败，客户端仍需定义保留输入、结束等待和恢复操作的方式。

重试会不会重复写入或扣费，需要单独约定。涉及不可重复的操作时，讨论幂等标识、去重范围、有效期与并发行为；界面禁用重复点击不能保证服务端只执行一次。上述同步示例允许显式重新生成，因此应告知它可能产生新的结果和调用成本。

## 6. 用 Mock 与小试验检查方案

### 从同一份契约生成样例

Mock 用来模拟交互，让界面和服务端能够基于相同约定推进。准备成功、输入错误、处理中、超时和外部失败等与本期有关的情况，保持字段和状态含义一致。

浏览器与 Node.js 项目可选择 [MSW](https://mswjs.io/docs/) 模拟网络交互。其他环境可以采用适合的平台桩或测试服务。工具服务于契约，不要求所有客户端共享同一种拦截机制。

Mock 验证消费方是否能处理约定结果；真实接口还需要验证实际响应与契约一致。字段缺失、空值、错误码和版本变化都可能暴露偏差。AI 输出的结构检查，也不能代替对答案与原文关系的内容检查。

### 为关键风险保留真实验证

对练习示例，使用少量经过审核的代表性材料调用真实生成链路，记录是否返回 3 道有效题目、答案依据、耗时和成本。模拟上游失败与异常输出，检查失败结构和输入恢复；再验证目标运行环境，而不是只确认本地成功。

小程序选型则检查目标端编译、预览、关键平台接口和真机表现。试验失败时，更新架构选择和相关契约；它可能意味着缩小输入范围、调整等待方式，或重新考虑技术方案。

---

## 7. 保存重要架构决定

### 记录理由、代价与重新考虑条件

对会影响系统边界、数据、兼容性或运行方式的决定，使用简短的 [架构决策记录（ADR）](https://adr.github.io/)。它保存一个决定的背景、理由和后果，让后续开发者或新的 AI 对话能够恢复判断依据。

```prompt
决定名称与日期：
状态：提议 / 已采纳 / 已替代
对应的产品需求与约束：
比较过的方案：
选择与主要理由：
依据、对应版本与验证结果：
接受的代价与尚未验证的假设：
对职责、数据、契约和运行方式的影响：
重新考虑的触发条件：
替代记录或相关材料：
```

例如，“先采用同步生成”可以记录：当前只验证单次练习，目标环境试验满足等待预算时采纳；接受失败后需要显式重试；若耗时、恢复需求或平台限制变化，再评估任务化处理。试验尚未完成时保持“提议”，不把预期效果写成验证结果。

技术清单与架构决定一起更新。契约变化时同时检查消费方、Mock 和验收样例；是否保留旧接口、增加版本或协调升级，依据实际兼容需求决定。跨语言或多人、多个 AI 任务协作时，指定同一份契约为当前依据。

## 8. 审查并交接下一阶段

### 检查需求、结构与契约是否一致

```prompt
请作为没有参与前面讨论的评审者，检查架构与契约是否足以支持本期产品。

产品定义与验收：【粘贴】
架构职责、核心流程与选型决定：【粘贴】
契约、Mock 样例与已做试验：【粘贴或链接】
未解决问题：【填写】

请检查：
1. 每项核心需求是否有明确负责的部分，关键数据与状态是否能沿流程追踪。
2. 选型是否适配目标平台、现有能力和约束，有没有缺少理由的复杂度。
3. 契约是否覆盖输入输出、空值、状态、错误、权限、等待、重复操作与必要的兼容要求。
4. 文档、样例、Mock 与验收是否一致，结构校验和业务质量是否分开验证。
5. AI 建议中的版本和能力判断是否有来源或验证依据，未知项是否被当成结论。
6. 哪些问题阻塞下一阶段，哪些可以带着明确的验证计划继续。

按“位置、具体问题、影响、建议动作、是否阻塞”列出结果。
不要补造测试结果或擅自扩大范围。提出最多 5 个需要决定的问题，最后给出有条件的交接判断。
```

### 交接一份可以使用的当前版本

交接材料包括当前 PRD、结构与流程说明、契约和样例、重要决策及未解决问题。每个关键未知项说明影响、验证方式和决定时机。若实际已有架构，标明本次变化与必须保持的行为。

下一阶段的 UI 原型据此安排输入限制、等待、失败、重试和结果状态，开发据此实现与校验。若关键平台能力或运行条件仍可能使核心流程不成立，先完成必要试验；若影响用户价值和范围，回到产品定义同步修改。

运行部署、详细存储配置和框架安装可以留给后续章节。架构和契约在实施中继续更新，目标是让当前产品有清楚、可验证且维护得起的实现路径。
