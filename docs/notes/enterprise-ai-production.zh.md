# 【AI 开发工作流 · 08】 从个人 Demo 到企业级平台：一张升级地图与一个视频案例

前几章把想法变成了可以运行、可以部署的产品。接下来，把链接交给其他人，问题才逐渐出现：别人能看到我的文件吗？长任务能不能关掉网页以后继续？同时来了很多用户怎么办？模型更新以后，结果会不会反而变差？

Coding Agent 已经能帮助我们实现很多功能。作为产品的建设者，仍需要知道**该补哪些能力、为什么现在需要、怎样判断它真的做好了**。本章先建立这张地图，再把地图变成可以交给 Agent 的小任务。

全文沿用一个教学案例：一个“上传视频，生成带时间戳的摘要”的个人工具，逐步开放给同事、团队和企业客户。以下是升级方案的示例，不代表已有产品实现，也不预设每个工具都必须用上。相关技术资料核对日期为 2026-10-30。

## 1. 先看全貌：平台升级可以从六个问题展开

个人使用时，你知道文件放在哪、可以手动重跑脚本，也能接受偶尔等待。一旦其他人开始依赖它，产品就要替用户处理这些事情。先用下面六个问题定位缺口：

六个分支会相互影响。例如，后台任务要保存“是谁提交的”，排队要考虑“谁先处理”，加速也不能绕过权限或牺牲完整性。它们是一张能力地图，可以按实际问题逐步补齐。企业级平台也可以从一个应用、一个数据库和少量后台处理进程开始。

## 2. 谁能使用：让每个人有自己的数据与操作边界

**视频案例：** A 上传了内部会议，B 改一下链接就看到了摘要。要补齐的是**身份与权限管理**。

**登录、角色和归属，各管什么？**

| 概念 | 要解决的问题与例子 |
| --- | --- |
| **身份验证** | **你是谁？** 确认当前登录的是哪位成员 |
| **角色权限** | **你能做什么？** 成员处理视频；管理员邀请成员、管理额度 |
| **资源归属** | **能操作哪份资料？** 自己的视频、团队共享视频，各有范围 |

**最终访问权要结合三者判断。** 同样是“成员”，也不能访问其他团队；管理员是否能读私有视频，也要单独规定。

**把规则落实，可以分三步：**

1. **先定默认规则。** 视频默认私有还是团队共享？谁能删除、导出、邀请成员或调整额度？把动作和允许执行的人写清楚。
2. **服务端核验每次访问。** 根据已验证身份判断归属；覆盖原视频、转写、摘要、搜索、下载和后台任务。隐藏按钮无法阻止直接调用接口，数据库也可设置访问规则，见 [Supabase 行级安全文档](https://supabase.com/docs/guides/database/postgres/row-level-security)。
3. **权限变化后重新判断。** 成员离职后，旧任务编号不应继续开放访问；后台生成完毕也要按当前权限展示。下载链接需要有效期与失效策略，已下载的副本则无法自动收回。

**资料生命周期也要交代：**

- **发给谁：** 哪些文件会进入外部模型或转写服务？
- **留多久：** 原视频、转写和中间文件分别保存多久？
- **怎样删除：** 删除原视频时，哪些摘要、片段和临时文件需要一并清理？

**怎么验收：** 用两个账号、两个团队，尝试跨账号读取、修改和下载；再移除一个成员，检查旧入口是否仍可访问。密钥留在服务端，字幕中的恶意指令不能扩大权限，原因见 [OWASP 提示词注入说明](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)。

## 3. 任务怎样运行：网页离开了，工作仍能继续

**视频案例：** 长视频处理到一半，用户关掉网页，回来只能重新开始。需要把处理过程从一次网页请求中分离出来。

**先认识三个概念：**

- **异步处理：** 先登记任务、返回查看入口，后台继续工作，用户不必一直守着页面。
- **消息队列：** 保存等待处理的工单，由空闲执行者领取；通常传任务编号，不传整部视频。
- **Worker：** 真正执行下载、转写和总结的后台进程。

它们与前台、数据库和文件存储的关系如下：

[![网页离开后，后台任务怎样继续 — 前台接单与后台执行分开；页面读取已保存的任务状态与结果。](/notes/enterprise-ai-production/production-task-flow.zh-4330a3a09630.webp)](/notes/enterprise-ai-production/production-task-flow.zh-4330a3a09630.webp)

*前台接单与后台执行分开；页面读取已保存的任务状态与结果。 [查看原图](/notes/enterprise-ai-production/production-task-flow.zh-4330a3a09630.webp)*

**任务状态要真实、可找回：**

- **数据库记进度：** 谁提交的、当前阶段、哪些片段已完成、结果在哪里。
- **文件存储放成果：** 原视频、音频、转写和摘要等文件；队列负责通知有工作。
- **页面读已保存状态：** 可定期查询或接收推送。百分比不可靠时，显示“转写中，已完成若干片段”。

**“接单”到“执行”之间，也可能掉链子：**

- **已登记、未入队就崩溃：** 要能发现并补送这项工作。
- **Worker 领取后退出：** 要能识别长期未推进的任务，安全接手；恢复和防重复见第 6 节。

> **先分工，再选工具。** 前台和 Worker 可以在同一个项目中；早期也可复用托管任务服务，或具备可靠领取与恢复机制的数据库任务表。异步让用户能离开，队列安排等待，实际提速还要看处理能力。

**怎么验收：** 关页后继续处理；重新登录能找到进度；服务重启后，已登记任务和已保存成果仍能找回。

## 4. 怎样更快：让用户尽早拿到有用的结果

**视频案例：** 任务已经能在后台运行，但用户仍要等很久。先分清你要改善哪一种等待。

**三个时刻，分别计时：**

- **已受理：** 收到任务，给出查看入口。
- **首个有用结果：** 可以读到有来源的转写或摘要片段。
- **完整完成：** 全片处理完，完整摘要可用。

模型的**首 Token 时间（TTFT）**只覆盖其中一段。“正在处理”或一句客套话出现得早，不代表用户已拿到有效内容。

**先定位瓶颈，再选办法：** 记录上传/下载、排队、转写、生成和传输各花多久。下载和排队占了大头，换更快的生成模型也未必有效。

**改善等待体验：流式返回**

- **边生成边展示。** 不必等全部文字完成；SSE 是一种实现方式，见 [MDN 服务端事件说明](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)。
- **检查整条链路。** 服务端陆续输出，页面却最后一次显示，仍未达到目标。
- **支持回来继续看。** 断网后从保存的状态和结果接上；页面连接断开，不应自动取消后台任务。

**减少实际工作：长视频分段处理**

[![长视频：分段并行，按时间轴归并 — 可用字幕走捷径；分段独立恢复，完整概览通过覆盖检查后发布。](/notes/enterprise-ai-production/production-video.zh-ec8ef36355ef.webp)](/notes/enterprise-ai-production/production-video.zh-ec8ef36355ef.webp)

*可用字幕走捷径；分段独立恢复，完整概览通过覆盖检查后发布。 [查看原图](/notes/enterprise-ai-production/production-video.zh-ec8ef36355ef.webp)*

1. **优先利用合格字幕。** 有权使用且内容适用时，可以跳过转写；否则提取音频，做语音转文字（ASR）。
2. **分段、有限并行。** 保留原始时间位置，处理切口重叠和乱序完成。文件切段与语义分章不同，媒体边界见 [FFmpeg 分段文档](https://ffmpeg.org/ffmpeg-formats.html#segment)。
3. **先展示有依据的部分结果。** 例如访谈前几个时间段的要点；标清已覆盖范围，缺失片段不能装作已完成。
4. **最后做全局汇总。** 核对全片覆盖，归并重复观点、连接跨段讨论；重要人名、数字和结论能回查原文。不能只把片段摘要拼接起来。

**另外两个常见优化点：**

- **缓存复用：** 相同视频和设置可复用已获授权的结果；核对内容版本、访问权限与保存期限。
- **合理分工：** 普通代码处理切分、时间和格式检查；模型负责理解与归纳。较轻模型是否够用，要用代表性样本比较。

> **别漏掉画面。** 幻灯片、图表和屏幕演示可能承载关键内容，需要按目标补充与时间对齐的画面分析。

**怎么验收：** 同时比较首个有用结果、整片完成时间、费用和摘要质量；分段、流式或增加 Worker 本身不等于已验证的提速。

## 5. 人多了怎么办：让任务有秩序地使用有限资源

**视频案例：** 一部长视频发出全部片段请求，其他人的短视频一直排不上。这是**高并发与资源调度**的问题。

**先分清，哪一部分在忙：**

- **很多人查看列表：** 主要压力在网页接口和数据库，可能需要减少重复查询、优化读取。
- **很多人提交长视频：** 主要消耗带宽、转写资源和模型额度，需要控制后台执行量。

多人同时工作是**并发**；一部视频同时处理多个片段是**并行处理的一种安排**。两者会争用同一批资源，不能各自无限放开。

**按三步控制容量：**

1. **限流与配额：控制进入量。** 限制短时间提交次数，以及用户或团队可用的视频时长、任务数或费用。平台、团队、单个视频都需要适用的上限。
2. **公平调度：控制谁占多少。** 限制一项任务同时处理的片段数，让不同用户都能推进。长短视频成本不同，可按时长、大小或估算费用安排，并给估算误差留余量。
3. **找到瓶颈后扩容。** 网页实例分担请求，Worker 分担后台工作；关键状态需要共享持久保存。模型额度已用满时，加 Worker 可能只会增加报错。

**别只看“队列里还有几个”：**

- **等了多久：** 最早任务是否一直不动？
- **完成多少：** 高峰过去后，积压能否消化？
- **卡在哪里：** 是否频繁触发模型限额，或某一步特别慢？

排队过长时，应解释等待或暂时拒绝新任务，并给查询、取消和管理员处理保留余量。[AWS 队列积压文章](https://aws.amazon.com/builders-library/avoiding-insurmountable-queue-backlogs/)解释了处理能力与积压恢复的关系。

**怎么验收：** 混合测试多人同时提交、长短视频和持续大量提交。检查普通用户能否完成任务、长任务是否挤占他人、等待是否可解释、费用是否可控；目标来自实际测量。

## 6. 出错以后怎么办：保留成果，让任务能够继续

**视频案例：** 30 个片段完成了 27 个，服务突然重启。用户希望继续剩下的工作，不想重新付出整片处理的时间和费用。

**不同故障，采用不同处理方式：**

| 遇到的情况 | 怎样处理、守住什么边界 |
| --- | --- |
| 临时网络故障 | **等待后有限重试。** 次数、总时长和费用有上限 |
| 权限不足、文件不支持 | **停止并提示修正。** 不靠重复调用碰运气 |
| Worker 退出或服务重启 | **从保存的进度继续。** 先验证成果完整、版本适用 |
| 外部操作超时、结果未知 | **先查证，必要时人工处理。** 未查清前不重复写入 |

超时不证明远端没执行成功；具体原因见 [AWS 重试设计说明](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)。大面积故障时，还应错开重试、延长等待，必要时暂停调用，保留可恢复任务。

**三个机制，分别补齐：**

- **断点恢复：保住已完成工作。** 每段记录视频版本、时间范围、检查结果和文件位置。文件存在不代表写完整；恢复前核对，输入或设置变化后判断能否复用。
- **幂等：同一次操作不重复产生效果。** 双击、断网重发、重复投递不应创建两份收费任务；主动改设置再生成属于新操作。需要执行记录和接口支持。
- **取消：明确停到了哪里。** 停止后续调度，不等于已经发给外部的请求和费用会自动撤销。可支持的补偿按业务与接口执行，查不清则人工接管。

> **回退代码不能撤销外部事实。** 通知已发出、费用已产生时，不能靠重跑全链路或回退版本“当作没发生”。

**怎么验收，可以故意制造三种情况：**

1. **中断服务：** 已完成片段仍在，只继续需要处理的工作。
2. **重复提交：** 同一次操作不会重复产生业务效果。
3. **持续报错：** 重试按预算停止，原因可见，并提供补材料、重试或管理员处理入口。

## 7. 怎样长期运营：知道结果好不好，也知道系统出了什么事

**视频案例：** 模型更新后摘要更流畅，却漏掉了后半段。接口成功，不代表产品结果合格。

**先把五件日常工作管起来：**

| 要管的事 | 视频工具里的最小做法 |
| --- | --- |
| **质量评估** | 留代表性视频，检查关键事实、全片覆盖和时间戳；变更前后比较 |
| **日志与告警** | 按任务追踪下载、转写、总结；异常有人收到并处理 |
| **费用** | 统计每个有效结果的转写、模型、存储和重试成本 |
| **版本发布** | 记录代码、模型、提示词与处理规则；先小范围验证，保留可回退版本 |
| **备份恢复** | 同时覆盖数据库与文件；演练找回任务、权限、视频和结果 |

**评估怎样避免“看起来不错”：**

- **样本有差异。** 长短视频、多人讨论、噪声、专业词汇、以画面为主的讲解都要覆盖。
- **检查可观察事实。** 数字、人名、重要结论能回查原文；不要求摘要只有一个固定答案。
- **代码与人工配合。** 格式和流程可自动测试；内容抽样复核，AI 评分需校准。对波动结果重复比较，见 [Anthropic 评估实践](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)。

**费用与运行记录，重点看这些：**

- **按任务串起来：** 卡在哪一步、排了多久、重试几次、最终花了多少；日志不放密钥和不必要的私有内容。
- **别只看平均值：** 长视频、持续重试和大批量用户，可能贡献大部分额外费用。
- **全程控预算：** 提交前查大小与额度，执行中限制消耗，完成后清理不再需要的中间文件。

**把维护变成有人负责的流程：**

1. **先有一个任务管理入口。** 按编号查失败阶段和费用，按权限重试或取消，留下管理员操作记录。
2. **演练发布与恢复。** 测试环境、少量用户逐步放行；在独立环境恢复指定任务，确认权限正确、文件能打开、结果能回查。
3. **明确服务约定。** 谁处理失败、多久回应，组织如何管理成员，数据导出和删除包含什么、何时完成。

**怎么验收：** 能发现质量退步，能定位失败任务，能解释费用，能恢复数据，并且用户知道遇到问题找谁。管理能力可以随规模逐步完善。

## 8. 怎么排顺序：围绕下一批用户最可能遇到的问题

地图帮助发现遗漏，实施仍要有先后。同一个产品可以按下面的阶段推进；权限和数据安全等基本边界从首次开放使用就要考虑。

| 当前阶段 | 优先补齐的能力 | 可以观察的结果 |
| --- | --- | --- |
| 从自己使用到同事试用 | 登录、资源归属、持久保存、失败提示、基本额度与备份 | 别人能独立使用，数据不会串到其他账号 |
| 开始处理长视频 | 后台任务、状态查询、分段、部分结果、失败恢复 | 关页不丢任务，失败后保留已有成果 |
| 开放给更多人 | 队列调度、限流配额、负载测试、监控告警 | 多人使用时仍可控，长任务不会持续挤占其他人 |
| 服务企业客户 | 按客户要求补组织权限、统一登录、审计、数据政策、发布与恢复流程 | 客户能管理使用边界，维护者能承担持续服务 |

先选择当前最影响使用的一项，完成从界面、服务端到数据保存的闭环，再继续下一项。单个应用也可以承载这些能力；引入微服务、更多 Agent 或复杂基础设施，需要有具体问题和验证依据。[Anthropic 的架构实践](https://www.anthropic.com/research/building-effective-agents)也建议从简单方案开始，再按任务需要增加复杂度。

## 9. 怎样交给 Coding Agent：把升级方向写成一个可验收的任务

有了地图，就可以把“帮我做成企业级”改成一个明确任务，例如：“关闭网页后视频仍在处理，回来能找到进度和结果。”你负责确认用户、优先级、数据边界和可接受的结果；Agent 可以帮助检查现有实现、解释缺口、修改代码并执行验证。

下面的提示词先让 Agent 判断缺口，再实施一项选定升级。填写当前项目的真实情况；没有测量过的指标先保留为待确认项。

```prompt
帮助我把这个个人 AI Demo 逐步升级为可供团队使用的平台。

项目与核心流程：<项目目录、输入、处理过程、输出>
目前谁在使用：<自己 / 同事 / 多个团队 / 企业客户>
当前最影响使用的问题：<例如：关闭网页后长视频任务丢失>
本次希望完成的升级：<例如：后台继续处理，重新打开能查看状态和结果>
数据与权限边界：<谁能看视频、转写和摘要；是否存在不同团队>
预算与限制：<已有技术栈、部署环境、费用、维护能力>

先检查实际代码，用通俗语言说明当前流程。
按六个方面定位缺口：身份权限、后台任务、响应速度、
多人使用、失败恢复、质量与运营。区分已有能力、缺失能力和未知项。
结合当前用户说明优先级；本次只实施上面选定的升级。

给出最小可行方案，解释为什么需要相关概念。
优先复用现有技术栈；新增组件时说明用途、替代方案和维护成本。
在当前授权范围内完成代码与必要配置，验证正常流程和相关失败路径。
涉及外部发布或不可逆操作时，沿用项目已有的授权要求。

验收要对应本次问题，例如关页后继续、重新进入能查看、
服务重启不丢已登记任务、重复提交不会产生重复业务效果。
如果涉及提速，同时比较首个有用结果、完整完成、费用和质量。
不要把生成的代码或未执行的测试计划当成已经验证的结果。
最后说明改了什么、实际验证了什么、还有什么未验证。
```

这一次升级完成后，再回到地图选择下一项。逐步积累的任务记录、权限规则、评估样本和运行证据，会让后续每次交给 Agent 的工作更明确，也更容易检查。
