# 【AI 开发工作流 · 02】 需求分析与产品定义：从初步想法到可验证的 MVP

> **阅读背景**
> 环境准备完成后，接下来要决定把开发能力用在哪个问题上。一个产品想法往往同时包含目标、功能、界面偏好和技术设想。开始编码前，需要把它们整理成明确的用户场景、第一版范围和验收标准，让后续设计与开发有共同依据。

这一阶段可以先围绕三个问题展开：**给谁用，解决什么痛点，先完成哪些功能。** 再沿着用户实际完成任务的过程，检查这些回答是否足够具体。

产出是一份可持续修改的短文档，说明用户、价值、完整流程、本期范围与验证计划，详细程度随产品调整。

先选择起点，再依次明确问题、调研、划定范围和审查。提示词替换【】即可使用，未知项标为“待讨论”。

---

## 1. 根据想法的清晰程度选择路径

已有框架可以直接审查，模糊想法可以通过对话探索，两条路径最终汇入同一份产品定义。

[![两条起点，汇入同一份产品定义 — 已有框架与对话探索可以互补；新证据出现时，回到仍不确定的部分。](https://media.qiannawang.com/notes/workbench-diagrams/v3/scope-paths.zh-c14fc73fcf19.webp)](https://media.qiannawang.com/notes/workbench-diagrams/v3/scope-paths.zh-c14fc73fcf19.webp)

*已有框架与对话探索可以互补；新证据出现时，回到仍不确定的部分。 [查看原图](https://media.qiannawang.com/notes/workbench-diagrams/v3/scope-paths.zh-c14fc73fcf19.webp)*


### 路径 A：从已有框架开始

把业务经验、人工需求梳理、用户反馈或功能清单交给 AI，检查功能服务于什么用户任务、为什么需要，以及哪些判断仍缺少依据。即使清单很完整，目标用户和核心价值也可以继续被质疑。

下面的提示词可以启动整轮产品定义；第二至六节进一步解释如何判断它给出的结果是否可靠。

```prompt
你是一位有产品分析与软件交付经验的产品顾问。
我已经有一个初步框架，请帮助我审查、完善并定义本期产品范围。

项目与阶段：【项目名称；新产品或已有产品迭代】
目标用户与场景：【谁在什么情况下使用】
核心问题与现有方式：【现在怎样处理，哪里存在困难】
期望结果：【希望用户完成什么任务或获得什么结果】
初步流程与候选功能：【粘贴我的人工梳理】
已有依据与材料：【反馈、观察、调研、竞品链接或其他材料】
已知约束：【时间、预算、业务、数据或运行条件】
如果是迭代：【当前行为、本次变化及需要保留的能力】

请完成：
1. 复述你对用户、核心任务和价值的理解，检查框架中的缺口与矛盾。
2. 区分已有事实、分析推断和待验证假设，指出最影响方向的假设。
3. 围绕关键问题补充必要调研，说明哪些结论会影响本期取舍。
4. 定义最短的完整用户流程，划分本期必须、后续候选和暂不考虑的功能，说明理由。
5. 整理一份简短 PRD，包含主要异常、验收标准与用户价值验证计划。
6. 列出需要交给后续设计与架构阶段的问题。

协作要求：
- 我的框架可以被质疑；请指出值得简化、调整或放弃的部分。
- 不要把候选功能或竞品功能自动列为本期需求。
- 对会显著改变用户、核心价值或范围的缺口，先集中提出最多 5 个关键问题，等待回答后再确定相关结论。
- 对不影响当前分析的问题，注明暂定假设，并继续可以独立完成的部分。
- 外部调研附来源与核对日期；无法核实的内容标为待核实，不要编造反馈或数据。
- 本次完成产品定义，详细技术方案与编码留到后续阶段。

请按“项目理解与关键问题、依据与假设、核心流程、范围取舍、简短 PRD、验证与交接”组织输出。
```

### 路径 B：从模糊想法开始

如果只能说出“想做一个学习工具”或“希望改善某项工作”，先聊最近一次困难、现在怎么处理和最希望改善的结果。每轮围绕少量问题追问，有了线索后再比较少量方向，暂时保留产品形态和功能选择。

可以只填写一段想法或一件真实经历，其他槽位留空。能够暂时说明用户、场景、困难和期望结果时，再整理一页探索小结，继续第二节。

```prompt
请作为产品探索伙伴，通过多轮对话帮助我逐渐明确想做什么。
我目前只有模糊想法，还不能完整定义目标用户、产品形态或功能。

我现在的想法或兴趣：【用自己的话描述，零散也可以】
相关经历或观察：【最近遇到的困难、工作中的问题，或看到的现象】
希望发生的变化：【如果有这个产品，希望自己或别人能有什么不同】
已知条件或偏好：【有就填写，没有可以留空】

请按下面的方式和我交流：
1. 先简短复述你目前理解的内容，每轮只提出 1–3 个最有帮助的问题，等待我回答后再继续。
2. 从具体经历、当前做法、困难和期望结果追问。必要时给出容易理解的例子，帮助我表达。
3. 当有足够线索时，提出 2–3 个候选方向，说明各自服务谁、解决什么问题，以及还需要验证什么，让我比较和反馈。
4. 每讨论完一个主题，简短整理已明确的内容、仍有分歧的地方和暂定假设。我可以随时修正或推翻。
5. 当我们能初步说明用户、场景、问题和期望结果时，先整理一页探索小结，与我确认它是否准确表达了想法，再继续讨论调研与 MVP 范围。

协作要求：
- 不要一开始要求我填完整需求表，也不要立即输出完整 PRD 或功能清单。
- 不要把你建议的方向写成我的决定，不要替我虚构用户需求或市场验证。
- 允许缩小、改变或暂缓方向；如果现有工具可能已经满足需求，也请提出。
- 需要外部信息时，围绕具体问题调研并附来源；无法核实的内容明确标记。
- 当前先探索问题与价值，暂不进入详细技术选型或编码。

请先根据我提供的内容，提出第一轮问题。
```

**两条路径可以单独使用，也可以互补。** 证据挑战用户或问题假设时，回到相关部分探索。对话结论仍需调研与真实反馈；采用现有工具或暂缓也是合理结果。

## 2. 明确用户和核心价值

### 把想法写成具体的使用场景

“做一个 AI 学习工具”可以作为方向，但还不足以决定第一版功能。“帮助用户提高学习效率”也需要继续展开：用户在学什么，什么时候需要帮助，现在怎样完成这件事，最费力的是哪一步？

可以用下面的句式写出第一版问题陈述：

> 对于【某类用户】，当他们【处于某个场景】时，现有的【完成方式】存在【具体困难】。产品希望帮助他们完成【核心任务】，并通过【可观察的结果】检验是否有用。

例如，以知识问答工具为例，可以先提出这样一个待验证的场景：

> 对于刚读完一段材料、希望检查理解程度的自学者，重读缺少明确反馈，手工编题和核对答案又比较费力。产品希望把材料转化为一轮练习，让用户通过答题与解析发现具体的理解盲点。

这个描述已经能指导取舍：题目与材料的对应关系、答题反馈和学习回顾值得优先讨论。排行榜、分享海报和数字人讲解，则需要另外说明它们对核心任务的作用。

### 选择第一批用户

同一个产品可以服务多类人，但第一轮验证最好有明确对象。学生自测、教师出题和企业培训都可能使用知识问答工具，它们对题目审核、成绩保存和权限的要求却不同。

| 需要明确的内容 | 可以追问的问题 |
| :--- | :--- |
| 目标用户 | 第一版优先帮助哪类人？他们具备什么背景？ |
| 使用场景 | 什么事情触发使用？在什么设备和环境下完成？ |
| 现有方式 | 用户目前使用其他产品、表格，还是人工处理？ |
| 主要困难 | 哪一步耗时、容易出错，或者无法完成？ |
| 期望结果 | 用户拿到什么结果后，会认为这次使用有价值？ |

这一轮回答可以来自自己的观察、实际业务经历、用户交流或现有使用记录。暂时没有依据的部分保留为假设，作为后续调研的输入。

## 3. 结合人工判断与 AI 调研

### 把已有材料变成调研问题

把前两节得到的问题陈述、已有观察和已知限制放在一起，找出最可能改变方向的缺口。将“了解竞品”缩小成能影响决定的问题，例如“首批用户能否接受粘贴文本”，或“业务是否必须保存操作记录”。优先核实一旦不成立，就会改变用户、核心流程或本期范围的假设。

业务背景需要由熟悉场景的人补充。数据权限、审批流程、内容更新方式和答案溯源要求都可能影响取舍。记录来源和仍缺少的材料，为每个关键问题安排下一步验证动作。

### 带着具体问题开展调研

可以交替使用支持联网检索的研究工具和日常对话工具：前者帮助寻找来源、了解现有方案，后者帮助整理材料、比较选择和起草文档。拿到会影响决策的信息后，应回到原始来源核对。

调研可以围绕以下问题展开：

- 用户已经通过什么方式完成任务？现有方式的局限是什么？
- 同类产品首先突出什么价值？用户从进入页面到得到结果，需要经历哪些步骤？
- 哪些功能直接支持核心任务，哪些服务于留存、协作或收费？
- 想法依赖哪些外部能力？数据、接口、成本或部署条件是否影响第一版？

竞品比较表应记录具体观察，例如首次使用流程、输入要求、结果形式和失败处理。将产品名称与一串功能勾选放在一起，仍然需要补充这些差异对目标用户的意义。

| 比较维度 | 建议记录的内容 |
| :--- | :--- |
| 服务对象与任务 | 页面明确服务谁，首先帮助完成什么 |
| 核心流程 | 开始使用的条件，以及得到结果的主要步骤 |
| 输出价值 | 用户最终获得文件、答案、报告，还是某项操作的完成 |
| 使用限制 | 支持的输入、额度、账户要求，以及观察日期 |
| 可借鉴的取舍 | 哪个安排适合当前场景，哪个需要重新判断 |

涉及用户行为的问题，需要补充用户交流或观察。例如，想知道首批用户是否接受粘贴文本，可以请符合场景的人拿最近一次使用的材料演示当前做法，记录卡住的步骤、已有替代方式和实际投入。访谈优先询问已经发生的经历；对尚未发生的使用意愿，保留为待验证假设。

### 区分事实与分析中的不确定性

AI 可以帮助提出解释和方案，但“听起来合理”还需要进一步检验。整理调研时，建议区分三种信息：

- **已知事实**：有可核对的来源、观察或记录，例如实际体验到的操作步骤。
- **分析推断**：依据事实作出的解释，例如某个前置步骤可能增加首次使用成本。
- **待验证假设**：仍需通过用户交流、原型或实际使用检验的判断，例如用户是否愿意为某项结果付费。

重要判断记录来源、核对日期和下一步验证方式。

**能实现不等于值得做。** 还要确认用户有这个任务，以及现有方式为何没有满足他们。

### 调研现有方案与证据

下面的提示词用于比较现有方案。需要用户交流或现场观察才能回答的问题，列为后续验证动作；来源只能支持它实际说明的结论。

```prompt
请围绕下面的产品问题，调研现有解决方式，帮助我作出本期范围取舍。

用户、场景与任务：【填写】
目前的完成方式与困难：【填写；未知注明】
最需要核实的问题或假设：【列出 1–3 个】
候选方案或来源：【链接或材料；暂无可留空】
已知约束与待决定的范围：【填写】

请完成：
1. 最多比较 3 种相关解决方式，包含适用的人工方式或通用工具，并说明它们如何完成同一任务。
2. 记录核心步骤、输入要求、输出、限制和对目标用户的影响；区分实际体验、文档描述与分析推断。
3. 对影响决定的事实提供原始来源链接和核对日期；无法访问或核实的内容标为未知，不要假装体验过产品。
4. 按“观察事实、分析推断、待验证假设”整理结果，指出哪些证据支持或挑战我的设想。
5. 给出继续、简化、采用现有方案或暂缓的建议，说明它会改变哪些范围决定，以及下一步最小验证动作。

使用可用的联网能力；若无法联网，只分析所提供材料并列出待查项。
不要虚构访谈、用户量或市场数据，也不要把竞品功能自动变成本期需求。
输出比较表、证据缺口和建议取舍；暂不进入详细技术设计或编码。
```

调研使用第一阶段已经准备好的联网能力。将影响取舍的发现写回问题陈述和假设清单，再进入 MVP 定义；不必为了补齐所有竞品信息而推迟范围决定。

## 4. 沿完整流程划定 MVP

### 找到最短的完整价值流程

MVP 即 Minimum Viable Product，最小可行产品。它用有限范围交付核心价值，并帮助检验一组明确假设。定义范围时，先说明这一轮最想验证什么，再决定做到什么程度。

知识问答示例先验证：一次完整练习能否帮助用户发现理解盲点。

[![MVP 保留完整的价值流程 — 示例仅验证单次练习；历史记录、更多输入方式与社交功能另行判断。](https://media.qiannawang.com/notes/workbench-diagrams/v3/scope-mvp.zh-0dd46e11aab0.webp)](https://media.qiannawang.com/notes/workbench-diagrams/v3/scope-mvp.zh-0dd46e11aab0.webp)

*示例仅验证单次练习；历史记录、更多输入方式与社交功能另行判断。 [查看原图](https://media.qiannawang.com/notes/workbench-diagrams/v3/scope-mvp.zh-0dd46e11aab0.webp)*


只有生成接口还不够，输入、练习、反馈和回顾需要组成完整任务。

先支持一种输入。回顾可以先是一页结果，分享、下载报告和历史趋势另行判断。

### 判断功能是否属于本期

“缺少它，核心价值是否仍成立”是一个有用的起点，还需要检查它是否承担本轮验证所需的条件。

| 判断维度 | 需要回答的问题 |
| :--- | :--- |
| 核心任务 | 缺少它，用户还能完成主要任务吗？ |
| 验证目标 | 缺少它，还能检验当前最重要的假设吗？ |
| 使用条件 | 缺少它，会不会使真实使用无法开展？ |
| 替代方式 | 第一轮是否可以通过更简单的界面、人工操作或较小范围实现？ |

跨次复习若是核心任务，历史就应进入本期。企业培训可能需要身份与记录；验证付费意愿则要观察购买行为。

数据库、知识库检索、账户和支付都应依据任务判断。已有知识库若是答案的必要来源，检索能力就可能属于核心流程；无需为了遵循固定的“轻量 MVP”清单而推迟。

### 写清楚做什么与暂缓什么

范围表最好同时记录推迟原因和重新考虑的条件。以下是知识问答工具的示例取舍：

| 本期范围 | 暂缓内容 | 后续重新评估的条件 |
| :--- | :--- | :--- |
| 单段文本输入 | 文档、视频、网页输入 | 首批用户需要处理这些来源，且文本流程已得到反馈 |
| 一种题型和逐题解析 | 多题型和配图 | 已确认不同题型能支持实际学习任务 |
| 本轮学习回顾 | 分享、报告导出、历史趋势 | 用户需要带走结果或持续复习 |
| 个人练习 | 多人对战和排行榜 | 已有明确的共同学习场景 |

同样的方法可以用于其他产品：下载工具先检验指定来源的下载流程，个人网站先明确访客应找到哪些内容，内部系统先选定一项能从发起走到完成的业务任务。

## 5. 把需求写到可以验收

### 从功能名称走到具体行为

“支持智能总结”“界面友好”“响应快速”表达了期望，还需要补充触发条件、输入、输出和异常处理。

每项核心需求可以用四个问题检查：用户在什么情况下发起，系统处理什么，用户得到什么，失败后如何继续。

例如，将“答题后提供反馈”展开为：

> 用户提交本题答案后，系统展示本题的正确答案、用户答案和解析。解析应能对应输入材料中的内容；用户查看反馈后，可以继续下一题。生成失败时，保留已输入材料，并提供清晰的提示与重试入口。

再分别检查正常流程和主要异常情况，包括空输入、不支持的输入、处理中、失败、重复提交，以及用户离开后是否需要恢复。只定义与本期任务有关的情况，并说明产品行为。

### 定义 AI 输出的质量要求

AI 功能需要说明用户怎样使用输出，以及什么样的错误会影响任务。对知识问答工具而言，可以检查题目是否依据输入材料、题干与选项是否明确、答案与解析是否一致。对总结工具而言，可以检查核心信息是否遗漏、结论能否回到来源、材料不足时如何表达。

先准备少量有代表性的输入样例，包括正常、边界和失败情况。逐项写明预期表现，再决定是否需要量化指标。质量、等待时间和单次成本的目标应结合实际场景确定，并区分期望目标与已经测得的结果。

### 分开检查功能完成与用户价值

功能完成与用户价值需要不同的依据，不能用一次成功演示替代真实使用验证。

| 对照项 | 功能验收 | 价值验证 |
| --- | --- | --- |
| 核心问题 | 系统是否按照定义工作？ | 用户是否因此解决了真实问题？ |
| 练习案例 | 能完成一轮答题；失败时保留输入；回顾对应本轮结果。 | 能发现未掌握的内容；实际带着新材料再次使用；了解继续或放弃的原因。 |
| 检查依据 | 代表性样例、边界与失败路径，逐项对照预期行为。 | 观察真实任务、有效结果与再次使用，分别记录行为和口头兴趣。 |
| 结论边界 | 确认实现符合约定，仍不能证明产品价值。 | 为继续、调整或停止提供依据，结论受试验场景限制。 |

把验证计划写成一次具体试验：谁参加、用什么真实任务、观察什么行为、何时回看结果，以及什么结果会改变决定。人数和门槛应在试验前根据场景确定。将完成任务、发现问题和再次使用等观察，与用户口头表达的兴趣分别记录。第六节的示例展示了这种写法。

## 6. 将产品定义整理为短 PRD

PRD 即产品需求文档。把前面形成的问题、依据、范围与验收放进同一份当前版本，记录已经作出的决定和未解决问题。第一版可以保持简短，以下模板适用于新项目或现有产品的一次功能迭代。

```prompt
产品名称或本次迭代名称

背景与问题
目标用户：
触发场景：
现有完成方式与主要困难：
依据与来源：

本期目标
用户应能完成的核心任务：
这次最需要验证的假设：

核心流程
从什么输入开始，经过哪些步骤，得到什么结果：

范围与取舍
本期包含：
本期排除：
排除原因及重新考虑的条件：

核心需求与验收
触发条件、输入与输出：
正常流程与主要异常：
验收标准和代表性样例：

已知约束
与本次任务有关的业务、数据、时间、成本或运行限制：
已经确认的条件与暂定假设：

验证计划
准备观察什么行为或反馈：
采用什么方式验证：
什么结果意味着继续、调整或停止：

待解决问题
影响范围的关键问题：
可以留到设计与开发阶段的问题：

决策记录
修改了什么、为什么修改、影响哪些流程与验收标准：
```

对现有产品，还应补充当前行为、本次变化，以及需要保留的既有能力。这样可以判断新增需求是否影响原有流程。

需求文档可以保存为项目中的 Markdown，也可以使用便于协作的文档工具。保持一份清楚的当前版本，将调研材料和较长记录作为附件或链接，避免多个文档同时表达不同范围。

### 示例：知识问答工具的短 PRD

下面把前文的零散例子整理成一份初稿。**这是用于说明写法的假设项目，尚无真实用户验证。** 输入长度、人数和判断门槛都是示例决定，实际项目应根据场景调整，并在试用前确定。

**背景与问题**：第一批用户是读完一段材料、希望检查理解程度的自学者。当前可能通过重读或手工编题自测，困难是难以发现自己没有理解的部分。这个判断目前来自产品设想，仍需访谈核实；尚无访谈记录或竞品体验证据。

**本期目标与假设**：让用户完成一次基于原文的练习，并指出一处需要重新理解的内容。待验证假设是：答题和对应解析能帮助用户发现具体的理解盲点。

**核心流程**：粘贴 200–2,000 字符的材料 → 生成 3 道单选题 → 逐题作答并查看解析 → 查看本轮错题与对应原文。

**范围与取舍**：本期包含文本输入、单选题、逐题解析和本轮回顾。账户、历史记录、文档与视频输入、分享、付费均暂缓，以便先检验单次练习的价值。若用户确实反复使用且需要跨次复习，再评估账户和历史记录；若主要使用材料无法通过粘贴处理，再评估其他输入。

**核心需求与验收**：

| 场景 | 可检查的预期行为 |
| :--- | :--- |
| 输入与生成 | 空白或超出长度范围时说明限制、保留输入，不发起生成。对于预先审核的 5 份有效样例，每份生成 3 道题，每题有 4 个选项、1 个正确答案、解析及对应原文片段；人工检查答案能从原文得出。材料不足以出题时说明原因，允许修改输入。 |
| 作答与回顾 | 提交后显示用户答案、正确答案和解析，再进入下一题。全部完成后，回顾页的错题和原文片段与本轮作答一致。 |
| 失败与重试 | 模拟生成服务失败时，在当前页面保留材料并提供重试入口；重复点击生成不会创建多轮练习。不承诺关闭页面后恢复。 |

**已知约束与待解决问题**：先在桌面浏览器验证单次流程，不保存跨次历史。生成耗时、单次成本和不同材料的出题质量尚未测量，需要在可行性试验中记录；若无法满足试用场景，就先缩小材料范围或调整流程。

**价值验证计划**：邀请 5 位符合场景的自学者，用他们有权使用的材料各完成一轮，并对照原文解释自己发现的理解问题。暂定继续条件是至少 3 人能指出一处经原文核对成立的理解盲点，且至少 2 人选择用新的材料再完成一轮并实际完成。若主要卡在输入或操作，先修正流程；若流程可用但无人发现有用的新信息，就重新检查问题和方案。这个小样本只用于决定下一次试验，不能证明学习效果。

**决策记录与交接**：初版选择文本和单次回顾，以减少输入解析和历史管理对验证的干扰。交给下一阶段的问题包括生成任务的等待与重试方式、必要的临时状态和测量方法；涉及范围的变化同步更新本 PRD。

### 用 doc-coauthoring 协作完善文档

材料较多、需要反复写作时，可以使用 Anthropic 的 [doc-coauthoring](https://github.com/anthropics/skills/blob/main/skills/doc-coauthoring/SKILL.md)。它提供背景收集、逐段完善和读者测试三个环节，适合将访谈、笔记和已有框架整理成 PRD。安装方法见 [Skills 目录](https://skills.sh/anthropics/skills/doc-coauthoring)：

```bash
npx skills add https://github.com/anthropics/skills --skill doc-coauthoring
```

这个 Skill 是可选的，不安装也可以使用模板和提示词完成文档。初稿整理完成后，进入下一节检查它能否被没有前文上下文的读者理解。

## 7. 审查初稿并持续修订

这一节检查已经写成的产品定义：哪些地方会被误解，哪些决定没有依据，哪些要求还无法验收。审查应得到具体问题和修改建议，再把必要修订写回第六节的同一份 PRD。

### 让没有前文上下文的 AI 审查

新开一个对话，只提供 PRD 和必要附件，检查它能否准确理解目标用户、完整流程、本期排除项和验收方式。这个做法也可用于上一节 Skill 的读者测试。让审查者指出缺口，避免用此前聊天中的解释代替正文。

```prompt
请作为第一次接触本项目的产品评审者，审查下面的产品定义。
仅依据提供的材料判断，缺失信息明确标为未知。

产品定义：【粘贴 PRD】
已有依据或附录：【粘贴或链接；暂无请注明】
本期时间与资源限制：【填写；未知可留空】

请检查：
1. 用户、触发场景、核心问题与期望结果是否具体且一致。
2. MVP 是否形成完整流程，是否存在可以简化或暂缓的功能，排除项是否破坏核心任务。
3. 哪些结论缺少依据，哪些把假设写成了事实。
4. 核心需求是否包含可执行的验收标准、代表性样例和主要异常处理。
5. 验证计划是否能检验用户价值，继续、调整或停止的条件是否清楚。
6. 不知道之前的对话，是否仍能据此理解范围并进入后续设计。

按“原文位置、具体问题、影响、建议修改、是否阻塞下一阶段”输出。
区分影响方向的问题与可以后续完善的问题；没有依据时不要直接判断为通过。
对阻塞问题提出最多 5 个关键追问，不要替我补造决定或擅自扩大范围。
最后判断是否可以进入下一阶段，并列出需要先解决的问题。
```

审查后优先处理会改变用户、核心价值、范围或可验收性的缺口，其他改进记录为后续事项。AI 给出的“通过”只是一项审查结果；是否进入下一阶段，由第八节结合未解决问题决定。

审查还应区分假设的验证状态与计划的完整程度。例如，第六节的试用尚未进行，只要目标、试验方法和决定条件清楚，就可以保留为待验证事项；若连准备观察什么都说不清，则应先补齐计划。文档审查本身不会产生用户验证证据。

### 在原文中批注并保留修改原因

无论从哪条路径开始，有了探索小结或需求初稿后，都可以直接在文档中标记问题：

```prompt
[TODO] 当前目标用户过宽，请拆分场景，并给出首批用户的选择建议。
[待核实] 这个限制来自哪条来源？核对后再决定是否排除该输入。
[范围决定] 本期先支持文本，保留其他输入作为后续候选。
[待补验收] “高质量解析”需要哪些样例和检查标准？
```

再让 AI 根据批注修订，并检查相关范围、流程和验收是否同步变化。已经确认的内容应进入正文；尚未解决的事项保留为待办；影响范围的决定记录原因。

开发期间有新想法时，先判断它是否影响当前核心任务。若会改变本期目标，就同步修改需求和验收；其余进入后续候选。这样既能吸收新的认识，也能保留当前版本清楚的完成边界。

## 8. 决定下一步并交接

完成审查与修订后，根据剩余问题决定下一步。允许带着已标明的假设继续推进，但不能把会改变方向的缺口默认为已经解决。

| 当前情况 | 下一步 |
| :--- | :--- |
| 用户与核心任务明确，范围和验收可执行，剩余问题主要属于实现方式 | 进入 Architecture & Contracts，讨论技术方案与接口契约 |
| 输入、任务时长、数据使用或外部能力的不确定性可能让核心流程无法成立 | 先做小范围可行性试验，记录结果后调整 PRD |
| 用户、问题或核心价值仍不清楚，现有依据无法支持方向 | 回到问题探索或用户调研，也可以缩小方向或暂缓开发 |

交接材料以当前 PRD 为入口，附上相关证据、验收样例和未解决问题。每个重要的未解决问题说明它会影响什么决定，以及准备怎样确认；将需要保存的结果、跨设备继续的要求、允许等待多久和外部能力失效时的预期行为写入对应需求。

下一阶段据此讨论技术选型、数据模型和接口契约。架构试验或实际使用带来新发现时，回到第七节的修订方式，同步更新范围、验收和决策记录。
