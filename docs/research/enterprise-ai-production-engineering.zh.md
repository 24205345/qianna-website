# 【AI 开发工作流 · 08】 从 Demo 到企业级 AI 平台：可靠性、并发与长任务设计

> **阅读背景**
> 前七个阶段将想法推进到可使用、可保存、可部署的产品。部署完成之后，还需要回答另一组问题：换一批用户是否仍然有效？任务中断后能否恢复？模型犯错时，系统能否守住权限、资金、数据和成本边界？

**Demo 证明一条路径可行；生产级产品需要证明，在约定范围内持续交付结果，并能处理范围之外的情况。** 企业级平台进一步要求：多个团队能够在统一的身份、权限、审计和运营规则下使用它。

本章用两类任务贯穿设计：企业知识与服务助手解释权限、工具和外部副作用；长视频提取与总结解释首个结果、分段并行、资源调度和断点恢复。前者先做只读问答，再开放经过确认的写操作；后者先跑通提取，再证明速度、覆盖与成本。是否增加 Agent 由任务决定。文中的架构、阈值与数据均为教学设计，需按业务实测确定。

按“价值与边界 → 平台架构 → 执行与恢复 → 数据与安全 → 评估发布 → 交互延迟与并发 → 长视频流水线 → 运营与交付”阅读。资料链接放在对应论点附近，区分框架提供的能力、应用需要落实的保证，以及需要实际测量的指标。参考资料核对日期为 2026 年 10 月 30 日。

## 1. 先定义生产标准，再决定需要多少 AI

### 把“能回答”改写为业务结果

第一步是选定一个有明确负责人的任务，并与当前人工流程或已有系统比较。记录用户、输入、交付结果、错误影响和人工接管方式。离线跑分提高，只有转化为业务效果才值得继续投入。

| 问题 | 企业助手的设计示例 | 应保存的依据 |
| :--- | :--- | :--- |
| 谁在什么场景使用 | 员工查差旅政策；服务团队接收工单 | 真实任务样本、使用权限、业务负责人 |
| 怎样算完成 | 答案引用适用政策；确认后仅创建一张正确工单 | 验收规则、系统中的最终状态 |
| 怎样衡量价值 | 缩短解决时间，同时控制错误率与人工复核负担 | 人工基线、任务完成率、单次成功任务成本 |
| 哪些错误不能放行 | 越权读取、重复创建、伪造引用、泄露敏感材料 | 阻断规则、对抗样例、响应预案 |
| 失败后谁接手 | 转交指定服务队列，并附已完成步骤 | 接管责任、响应目标、操作手册 |

区分三个容易混淆的指标：**可用性**衡量服务能否被调用；**任务质量**衡量结果是否正确；**业务价值**衡量结果是否真正节省时间、增加收入或减少损失。HTTP 200、语言流畅和用户点赞都不能单独代表任务成功。

### 在传统代码、Workflow 和 Agent 之间选择

| 任务特征 | 优先候选 | 例子与取舍 |
| :--- | :--- | :--- |
| 规则和状态转换明确 | 传统代码、规则引擎、数据库事务 | 配额扣减、权限检查、订单状态流转；规则由代码实施 |
| 步骤基本固定，部分步骤需要理解语言 | Workflow，在固定流程中嵌入模型调用 | 文档解析 → 检索 → 生成 → 校验；容易逐步评估和排错 |
| 下一步取决于执行中获得的新信息 | 有边界的单 Agent | 跨多个知识源调查问题；允许选择工具，但限制可执行动作和预算 |
| 子任务可独立开展，且收益经过验证 | 多 Agent 或并行工作流 | 分别研究互不依赖的资料；需承担协调、合并和额外调用成本 |

工作流也可以有条件分支、循环和人工审批，不必都表达成 DAG。Agent 可以在授权范围内动态选择下一步，最终的状态迁移、工具执行和权限判断仍由运行时代码负责。Anthropic 的架构实践同样建议从简单组合开始，根据任务需要增加复杂度。[Building effective agents](https://www.anthropic.com/research/building-effective-agents)

**本节交付物：** 一页生产化任务说明，包含人工基线、业务成功条件、风险边界、负责人和架构选择理由。

## 2. 搭建平台骨架：把体验、执行、模型和业务数据分开

“企业级”不等于微服务、Kubernetes 或自建模型。小团队可以从模块化单体、关系数据库、对象存储和一个后台 Worker 开始；只有耗时任务、隔离或扩容需要时，再拆出独立服务。

先看一次任务跨过哪些边界：模型可以提出动作，服务端执行器和工具网关决定是否放行，并保存可查证的业务结果。图中的职责可以位于同一应用内；策略、版本、观测和审计贯穿整个过程。

[![规划与执行，遵守不同的边界 — 模型提出候选动作；服务端校验、授权并记录业务操作。](/notes/enterprise-ai-production/production-boundaries.zh-cfe9c13cf36b.webp)](/notes/enterprise-ai-production/production-boundaries.zh-cfe9c13cf36b.webp)

*模型提出候选动作；服务端校验、授权并记录业务操作。 [查看原图](/notes/enterprise-ai-production/production-boundaries.zh-cfe9c13cf36b.webp)*

这些职责分别需要落实以下能力与约束：

| 层次 | 主要职责 | 必须守住的边界 |
| :--- | :--- | :--- |
| 工作界面 | 输入、进度、证据、确认、取消、人工接管 | 提交成功与执行成功分开呈现；刷新后仍能查询任务 |
| 身份与接入 | SSO、组织成员、角色、请求限流 | 从已验证身份解析租户；服务端判断资源权限 |
| 应用编排 | 任务状态、队列、审批、重试、截止时间 | 控制状态迁移、任务预算和恢复入口 |
| 模型与上下文 | 提示词、模型路由、结构化输出、检索与记忆 | 模型返回候选动作；输出必须经过校验 |
| 工具网关 | 工具白名单、业务校验、凭据、幂等与外部调用 | 每次执行重新鉴权；模型不持有通用管理员凭据 |
| 数据与证据 | 业务记录、原始资料、索引、任务日志、结果 | 区分权威业务状态、派生索引和模型生成内容 |

**一次任务的流转：** 登录并校验成员身份 → 创建任务与预算 → 入队 → Worker 读取任务 → 组装授权上下文 → 模型提出动作 → 工具网关校验并执行 → 保存结果与进度 → 返回可验证的业务结果。

至少区分这些标识：`tenant_id` 标识组织，`user_id` 标识操作者，`task_id` 标识业务任务，`attempt_id` 标识某次执行尝试，`operation_id` 标识某次业务写操作，`trace_id` 连接观测链路。一次任务重试可以产生新的执行尝试和 Trace，但同一个业务写操作应复用其稳定的幂等标识。

前端需要“排队中、处理中、等待确认、结果待核实、部分完成、失败、已取消”等真实状态。模型停止输出或用户关闭页面，都不能直接等同于后端任务结束。

**本节交付物：** 职责图、任务数据模型、身份传播方式，以及每项数据的保存位置与保留规则。

## 3. 设计有边界的执行器：模型可以规划，代码负责放行

### 把工具调用当成外部输入

结构化输出或 JSON Schema 能限制输出形状，却不能证明客户存在、金额合理或调用已经获授权。工具执行前至少检查四层：

1. **结构：** 工具是否存在，参数类型和必填字段是否正确。
2. **业务：** 对象是否存在、状态是否允许、金额或数量是否合理。
3. **权限：** 当前用户与租户是否能对这一对象执行这一动作。
4. **执行条件：** 是否通过必要审批，预算是否足够，任务是否已取消或过期。

例如，员工要求“替我创建门禁工单”。模型可以提取位置和问题描述；服务端应从认证身份绑定申请人、判断可见地点、生成工单预览，并在确认后调用创建接口。不能把模型生成的 `tenant_id` 或“管理员已批准”当作可信依据。

### 用状态机承接不确定性

| 当前状态 | 事件或条件 | 允许的后续动作 |
| :--- | :--- | :--- |
| queued | Worker 取得有效执行租约 | 进入 running，并记录执行尝试 |
| running | 需要敏感写操作 | 生成动作预览，进入 awaiting_approval |
| awaiting_approval | 有权用户批准且参数未变化 | 重新校验权限和业务状态，再执行 |
| running | 外部写请求超时，结果不明 | 进入 reconciling，查证外部结果 |
| running | 可恢复错误且仍在预算内 | 有界重试或受控重规划 |
| 任一活动状态 | 到达截止时间或收到取消 | 停止发起新步骤，核查已在执行的写操作 |
| reconciling | 无法自动确认结果 | 进入 needs_review，保留证据交给人工 |

这张表是简化示例，真实系统还应定义成功、失败、部分完成等终态，以及谁能触发每种转换。审批应绑定具体动作、参数摘要、有效期和版本；参数变化后重新审批，恢复执行时再次校验，防止审批与执行之间对象状态发生变化。

同时设置**模型轮数、工具调用数、累计 Token 或费用、总时长、单工具超时、并发和输出大小**上限。针对重复调用相同工具和相同参数、连续无进展等情况提前终止。上限应根据任务分布测量，不能把“最多五步”当成通用答案。

错误返回可包含 `error_code`、是否可重试和经过脱敏的修复提示。权限失败通常应终止该动作；缺失参数可询问用户；暂时性接口故障可按策略重试。不要让模型通过不断换工具尝试绕开拒绝。

**本节交付物：** 状态转换表、工具契约、执行预算和错误分类。

## 4. 做好重试、幂等与恢复：超时不代表没有发生

### 按操作语义决定是否重试

不能把“读操作可重试、写操作不可重试”作为绝对规则。关键在于副作用、幂等保证、错误性质，以及是否仍在总预算内。AWS 的可靠性资料特别提醒：请求超时不代表远端没有执行；有副作用的调用需要相应的幂等设计。[Timeouts, retries, and backoff with jitter](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)

| 情况 | 处理方式 | 需要注意 |
| :--- | :--- | :--- |
| 确认无副作用的读取遭遇短暂故障 | 有上限的指数退避与随机抖动；按接口约定处理 Retry-After | 控制全链路重试次数，避免 SDK、Worker、Agent 各自放大重试 |
| 写接口提供有效幂等保证 | 在接口契约允许时，以相同业务操作 Key 和相同参数重试 | 了解 Key 有效期、并发行为和失败结果缓存方式 |
| 写请求超时且远端结果未知 | 先按外部请求 ID 或业务操作 ID 查证，进入对账流程 | 不能立刻换新 Key 再写，也不能假定已经失败 |
| 参数错误、权限拒绝、资源状态不允许 | 修正输入、申请授权或明确终止 | HTTP 状态码只是线索，最终按服务错误契约判断 |
| 任务确认无法继续，且已发生副作用 | 根据业务规则补偿，或转人工处理 | 有些动作无法撤销；补偿也可能失败 |

幂等 Key 应表示“同一租户下的同一次业务操作”，在首次派发前持久化。它不应每次重试随机生成，也不宜只用订单 ID，以免把同一订单上的不同操作错误合并。Stripe 的 API v1 文档说明，相同 Key 会复用已保存的执行响应，参数不一致会报错；具体语义需按目标接口核对。[Idempotent requests](https://docs.stripe.com/api/idempotent_requests)

### Checkpoint 记录进度，业务台账记录事实

队列消息可能重复投递，Worker 也可能在“外部成功、本地未保存”之间崩溃。以创建工单为例：远端已创建工单，但响应丢失。此时应使用派发前保存的业务操作 ID 查证，拿回原工单，而不是换一个 Key 再创建一次。

[![写请求超时后，先查证再继续 — 远端可能已经成功；复用原业务操作 ID 查证结果，再推进后续步骤。](/notes/enterprise-ai-production/production-recovery.zh-ff558ff45cf2.webp)](/notes/enterprise-ai-production/production-recovery.zh-ff558ff45cf2.webp)

*远端可能已经成功；复用原业务操作 ID 查证结果，再推进后续步骤。 [查看原图](/notes/enterprise-ai-production/production-recovery.zh-ff558ff45cf2.webp)*

要让这条恢复路径成立，至少需要：

- **持久化任务进度：** 已完成步骤、输入输出引用、待审批动作、版本与预算；生产不能只用内存 Checkpointer。LangGraph 的持久化文档区分了持久检查点与重启后丢失的内存存储。[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)
- **业务操作台账：** 稳定操作 ID、参数摘要、调用状态、远端请求 ID 与查证结果；通过唯一约束、事务和并发控制避免两个 Worker 同时重复提交。
- **投递与恢复：** 业务状态和待发布事件需要一起可靠保存时，可考虑事务 Outbox；消费者仍需去重。租约到期与进程重启后，应能识别未完成工作。
- **重放边界：** 检查点恢复不等于外部操作只执行一次。恢复时复用已确认结果，对未知写操作先查证；重放评估默认使用沙箱或 Mock 工具。

### 补偿属于业务设计

创建工单后发送通知失败，通常应重试通知，保留已创建的工单。预留库存后支付确认失败，才可能需要释放库存。退款也不是把所有现实影响恢复到扣款前；邮件发出后更无法靠一个“撤回函数”保证收件人没看到。

只有跨多个步骤、需要业务撤销的流程才考虑 Saga 或补偿事务。补偿要有独立状态、幂等策略、失败告警和人工入口；执行顺序根据业务约束确定，不必机械逆序。Azure 的补偿事务模式也明确说明了这些限制。[Compensating Transaction pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction)

**本节交付物：** 重试矩阵、操作台账、恢复流程、对账与补偿手册。

## 5. 管理知识、上下文与记忆：先分清它们保存什么

### 三类信息不要混存

| 信息类型 | 保存内容 | 使用边界 |
| :--- | :--- | :--- |
| 业务事实 | 工单状态、订单、权限与审批结果 | 由权威业务系统读取，不能用对话摘要替代 |
| 知识资料 / RAG | 政策、产品文档、操作说明及其证据 | 需要来源、版本、适用范围、生效时间和访问权限 |
| 任务上下文与长期记忆 | 当前进度、待解决问题；经允许保存的跨会话偏好 | 短期按任务或会话隔离；长期明确用户、租户、用途和生命周期 |

检索是为当前任务找到证据；记忆是保存后续可能使用的信息。向量数据库不是所有状态的默认存储。LangGraph 的记忆概念文档也区分了会话范围的短期状态和跨会话的长期命名空间；命名空间仍需结合服务端授权使用。[Memory overview](https://docs.langchain.com/oss/python/concepts/memory)

### 把 RAG 拆成可诊断的链路

知识摄入时保存原始来源、稳定文档 ID、版本、访问控制、更新时间与生效区间，监测解析和索引失败。查询时先确定授权范围，再检索、重排、筛选证据并生成带引用的回答。

不要默认向量召回适合所有问题。政策编号、工单号和专有名词常需要关键词精确匹配；概念相似问题适合语义检索。混合检索与重排是可评估的候选，需比较质量、延迟和成本。[Azure AI Search：混合检索](https://learn.microsoft.com/en-us/azure/search/hybrid-search-overview)

“召回了相关文档但答错”应分开检查：

1. 解析或切块是否丢失标题、表格、脚注和适用范围。
2. 正确证据是否进入候选集，以及重排后是否仍在上下文中。
3. 是否同时取到不同地区、员工类型或生效期的政策。
4. 回答中的具体主张是否有对应证据，引用是否真的支持该主张。

新文档不一定取代旧文档。查询历史问题时可能需要当时有效的版本；不同地区政策可能同时有效。按适用范围和生效区间选择证据，对无法消除的冲突展示差异并请求确认。证据不足时，系统应回答“无法确认”或转人工。

### 让上下文保持小而完整

为系统规则、用户请求、证据、工具结果和输出分别预留预算。压缩时优先去掉重复工具结果和无关历史，保留目标、约束、审批、未决问题及证据引用。对金额、日期、ID 和权限状态保留结构化字段，避免只留自然语言摘要。Anthropic 的上下文工程资料讨论了压缩和结构化笔记的作用及信息丢失风险。[Effective context engineering](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

把“只依据资料回答”写入提示词是有用的，但不是可靠性保证；把 Temperature 设为 0 也不会消除幻觉或保证跨模型、跨基础设施的完全确定性。引用校验、结果验证和回归评估仍需保留。

长期记忆还需定义写入资格、来源、纠错、过期和删除规则。用户说过的话与模型推断出的偏好应区分记录；一次受污染的对话不能自动升级成组织共享知识。

**本节交付物：** 数据分类、知识元数据、检索评估集、上下文预算和记忆生命周期策略。

## 6. 建立企业信任边界：权限隔离与提示注入防御

### 租户隔离覆盖整条数据流

SSO 解决“是谁”，资源授权解决“能做什么”。租户身份必须来自服务端验证的成员关系，不能只信任请求参数。按组织角色和资源属性实施访问控制，并在数据查询和工具执行处落实。

隔离对象不仅是数据库行，还包括对象存储与签名链接、向量索引、缓存、任务队列、检查点、导出文件、日志和反馈数据。缓存 Key 要包含适当的租户与权限范围；共享索引必须确保过滤不会被绕过；权限撤销后也要处理已有缓存和下载链接。

Postgres RLS 可以作为数据库层防线，但要识别能绕过策略的角色、视图和服务凭据。Supabase 的文档明确讨论了 RLS 绕过情形；在后台代码里使用高权限客户端，并不会自动获得租户隔离。[Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security)

### 外部内容提供数据，不提供授权

网页、附件、邮件和检索片段都可能包含“忽略规则、上传文件、调用某工具”等恶意指令。它们进入上下文后仍是不可信内容。OWASP 将从外部资料进入模型的攻击归为间接提示注入，并建议结合权限限制和高风险动作的人类确认等防线。[Prompt Injection](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)

实际设计应同时覆盖：

- 工具和外部目标地址使用允许列表；抓取 URL 时防范 SSRF，限制内网地址、重定向和可访问资源。
- 工具凭据由服务端按最小权限注入；避免向模型暴露密钥或开放通用 Shell、任意 SQL 等高权限能力。
- 外部文本与系统规则分开标记；高风险写操作通过独立策略与审批放行。
- 文件解析、代码执行等任务使用适当沙箱和资源限制；隔离只是防线之一，不能替代权限判断。
- 输入、输出、日志与导出按数据分级脱敏；约定模型供应商的数据用途、保存方式和可接受处理范围。

系统还需明确保留期限、删除传播、备份处理和审计访问范围；具体要求根据客户合同、数据类型和适用规则确定。自托管模型或拿到一项认证，都不能单独证明整个产品满足所有要求。

**本节交付物：** 权限矩阵、数据流与威胁清单、跨租户负向用例，以及数据保留与删除流程。

## 7. 谨慎增加多 Agent：先证明分工的收益

当单 Agent 的问题来自工具描述不清、证据质量差或预算不足时，增加角色通常不能解决根因。先建立单 Agent 或固定工作流基线，再比较同一批任务上的结果。

多 Agent 更适合可以相对独立调查、需要不同上下文或权限范围的子任务。可采用中心协调者分配任务、专业 Agent 返回结果、统一合并的模式。也可使用其他拓扑，但每一种都应说明协调与恢复成本。

委托契约至少包含：子任务 ID、目标、输入与证据引用、允许工具、预算、截止时间、输出结构、完成条件和错误类型。每个子任务使用最小必要上下文；主 Agent 的权限不会因为“委托”而自动扩大，子 Agent 的结果也要校验。

生产中尤其要处理：重复分派、共享资源写入冲突、子任务超时、取消传播和部分成功。写操作尽量经过统一网关，由资源锁、版本检查或业务事务处理并发；不要让两个 Agent 各自认为自己负责最终提交。

比较时同时看任务成功率、证据覆盖、人工复核时间、总调用费用和端到端延迟。并行可以缩短部分等待，也可能被最慢子任务和汇总过程拖住；不存在“Agent 越多，效果越好”的普遍规律。

**本节交付物：** 与基线的对比报告、委托协议、共享状态所有权和失败合并策略。没有明显收益时保留更简单的方案。

## 8. 建立评估与发布门禁：验证结果，也验证过程

### 评测集从真实任务和失败中生长

先收集代表性任务，经过授权、脱敏和标注后组成版本化数据集。覆盖常见路径、长尾请求、无答案、知识冲突、越权、提示注入、超时、重复投递和取消。开发用例与保留评测集分开，避免不断调提示词后只记住题目。

先写清指标口径。例如，“自动完成率”可定义为在时限和预算内达到业务验收条件的任务数，除以已接受的适用任务数；同时报告拒绝、人工接管与未完成任务，避免仅挑选成功样本。正确拒绝越权请求可以通过安全评测，但不能计为完成了原业务操作。

| 评估对象 | 可采用的方法 | 需要避免的误判 |
| :--- | :--- | :--- |
| 任务完成 | 检查最终业务记录、状态及用户要求 | 模型说“已完成”不代表系统真的完成 |
| 工具执行 | 校验选择、参数、授权、调用次数与副作用 | 不强求唯一最短路径，允许合理替代方案 |
| 检索与回答 | Recall@K、引用支持度、关键事实覆盖、正确拒答 | 检索相关不等于答案正确 |
| 安全与隔离 | 权限、跨租户、恶意文件和注入测试 | 测试未泄露不代表现实风险为零 |
| 成本与性能 | 成功任务成本、P50/P95/P99、负载下的队列时间 | 平均延迟不能解释少数严重超时 |

确定性业务结果优先使用代码或数据库断言；开放式回答可结合明确量表的模型评审和人工复核。模型评审需要与人工校准，防范风格偏好、评分漂移和评测内容中的注入。对随机性较大的任务重复运行，报告样本量和波动，不能只展示“多跑几次至少成功一次”。Anthropic 的 Agent 评估实践区分了轨迹、最终结果和多类评分器。[Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

### 把 AI 配置作为版本化发布对象

一次行为变更可能来自应用代码、提示词、模型与参数、工具描述和 Schema、检索配置、索引快照或策略规则。为每次发布保存一个组合版本，并在任务上记录实际使用的版本；依赖供应商无法锁定时，至少记录可观测的模型标识和变更信息。

候选版本先通过离线评估与沙箱验证，再通过小范围试用逐步扩大流量。每个阶段都可以阻止继续发布；生产中的真实失败经过复核后，成为下一轮评测的用例。

首次开放能力时，可先做小范围只读试用，再逐步开放写操作。Shadow 流量只能执行不会产生真实副作用的路径，或连接沙箱；复制线上请求去真实创建第二张工单不属于安全的影子测试。

上线门禁同时包含质量底线、安全关键用例、延迟与成本预算、恢复演练。指标退化时停止扩大流量，回退兼容版本或切换到只读、人工处理。回退提示词不会撤销已经发出的邮件；旧任务如何继续使用原版本、是否需要迁移检查点，也应提前定义。

**本节交付物：** 版本化评测集、发布报告、灰度规则、回退与在途任务处理方案。

## 9. 把“响应快”拆成可测量的用户体验

### 受理、首字、首个结果与完成是四件事

一条请求很快返回“正在处理”，只能证明系统给出了反馈。模型开始输出时，检索、排队或转写可能已经消耗很久；长视频出现第一段摘要时，后半段也可能尚未处理。先约定用户到底在等什么，再讨论优化。

| 指标 | 建议的测量边界 | 容易混淆的地方 |
| :--- | :--- | :--- |
| 请求受理时间 | 用户提交到收到已持久化的任务 ID 与状态入口 | HTTP 202 或“处理中”不代表完成 |
| 模型首 Token 时间（TTFT） | 模型请求发出到首个内容 Token，单独记录供应商口径 | 不包含模型调用前的下载、排队与检索；协议心跳或元数据不算内容 |
| 用户首个有效内容时间 | 用户提交到界面展示可用回答或带出处的首段结果 | 若称“首字响应”，明确按模型侧还是用户侧计时；占位文案不计入 |
| 流式生成表现 | 内容 Token 间隔、长时间停顿、每秒输出 Token、断流率 | 平均输出速度好，不代表首字快或中途没有卡住 |
| 完整任务耗时 | 用户提交到全部处理、校验与结果持久化完成 | 首段摘要完成不代表整片总结完成；同时报告失败和取消 |

按问答、短文件、长视频分别观察这些指标的 P50 / P95 / P99，并记录输入长度、输出长度和负载。拆开上传或下载、队列等待、解析与转写、检索、模型输入处理、生成和后处理，沿实际依赖路径找到瓶颈。并行步骤看最长依赖链，不把所有步骤耗时简单相加。

### 流式传输改善等待体验，后台任务保存执行事实

交互问答可以在鉴权、证据准备和必要检查完成后流式返回内容。耗时视频任务则先可靠保存任务，再返回任务 ID；后台 Worker 推进，前端通过状态查询或事件订阅获取进度。不要让整段下载、转写和总结依赖一条持续开启的网页请求。

SSE 适合服务端向前端推送阶段、增量内容与终态；双向高频交互才考虑 WebSocket。SSE 的事件 ID 与重连机制只是传输能力，服务端仍需保存可恢复的状态或事件，按序去重并重新授权；原生 EventSource 与基于 fetch 的流式客户端也要分别处理重连。代理缓冲、空闲超时、连接数限制、流内错误和慢客户端都应实测。[MDN：使用服务端发送事件](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)

关闭页面或断流不自动取消后台任务。明确区分“重新订阅”“取消尚未执行的步骤”和“核查在途操作”。进度按阶段和已完成工作量呈现，例如“已转写 8 / 20 段”；动态分段或未知总量时显示已处理时长与当前阶段，不编造一个匀速增长的百分比。部分结果标记覆盖时间区间及版本，完整结果发布后再替换。

### 优化真正的关键路径

先去掉无必要的串行模型调用与重复检索，收紧输出长度；独立工作再考虑并行。缩短输入、复用允许缓存的稳定上下文、选择合适模型，都需比较首内容时间、完整耗时、质量和费用。缓存命中、模型侧输入处理、生成速度与用户端渲染分别测量。把请求改成 streaming，不会自动加快下载或 ASR，也不会保证任务总时长下降。

需要输出安全或结构化校验的场景，决定哪些内容可直接展示、哪些只能缓冲后发布；敏感原文不能因为“先流出去再检查”而绕过权限。**本节交付物：** 分任务的延迟预算、流式协议、进度与取消语义，以及包含慢连接和断流的验收记录。

## 10. 让并发有上限：容量、队列与公平调度

### 先算系统里积累了多少工作

并发用户数、每秒请求数、同时运行任务数、模型调用数和 GPU 使用量是不同维度。同一个长视频可以展开数十个分段请求；入口只限每秒请求数，仍可能让下游被单个任务占满。

在稳定吞吐、统计边界一致的条件下，可用“系统内平均任务数 ≈ 每秒完成任务数 × 平均停留秒数”做量级估算。例如每秒完成 2 个任务、平均停留 30 秒，意味着边界内平均约 60 个任务，并不代表只需 60 个 Worker；停留时间可能包含排队和等待。容量规划还要看突发、长尾、资源瓶颈与故障余量。队列也不会创造处理能力：持续进入速度超过完成速度，积压会不断增加。

| 控制位置 | 需要限制什么 | 过载时怎样处理 |
| :--- | :--- | :--- |
| 接入与租户 | 用户、租户和全局的活动任务、待办量、输入大小与预算 | 在昂贵处理前拒绝或明确排队，返回可理解状态 |
| 下载与媒体处理 | 连接、带宽、CPU、内存、临时磁盘、单文件时长 | 限制同时下载与转码，避免把文件全部读进内存 |
| ASR 与视觉处理 | GPU 显存、音视频秒数吞吐、批大小、模型驻留 | 按阶段设置工作槽位；必要时拆分 Worker 池 |
| 模型网关 | 同时调用、请求与 Token 速率、供应商配额、连接 | 全局与租户共同限额；重试遵守同一预算 |
| 分段任务 | 单任务展开数量、并发片段数、队列长度 | 完成一批再派发下一批，让其他任务获得机会 |
| 数据与输出 | 数据库连接、对象写入、缓存与流式连接缓冲 | 复用连接、控制批写与缓冲，隔离慢消费者 |

短问答与长视频可使用不同队列和并发池，同时保留共享模型、数据库和存储的总限额。对租户进行轮转或加权调度，为等待过久的批任务保留机会；一个付费租户也不能无限抢占全局资源。限制项需要在共享调度器中原子协调，不能只放在某个进程的内存计数器里。

队列要有长度与等待期限、最老任务年龄、重试次数和失败任务处理入口。队列满时让生产者减速或拒绝新任务，优先保留能在时限内完成的有效工作，而非接收后普遍超时。AWS 的可靠性实践分别讨论了过载时的有效吞吐，以及利用背压、优先级和隔离避免积压失控。[Load shedding](https://aws.amazon.com/builders-library/using-load-shedding-to-avoid-overload/)、[Queue backlogs](https://aws.amazon.com/builders-library/avoiding-insurmountable-queue-backlogs/)

### 批处理、扩容与压测都要围绕瓶颈

在模型和推理引擎支持时，小批合并可能提高推理吞吐，也可能增加等待和首结果时间；按长度分组、设置最大等待与独立交互队列后再比较。Triton 的动态批处理明确提供批大小与排队等待配置，这是吞吐和延迟之间的取舍，不是普遍提速开关。[NVIDIA Triton：Batchers](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/user_guide/batcher.html)

扩容看队列年龄、阶段吞吐、CPU / GPU / 显存和下游余量，不只看入口 QPS。增加 Worker 不会扩大供应商 Token 配额，也可能先耗尽数据库连接。预热、最小容量、扩容启动时间、熔断与降级都要纳入方案。

压测使用不同长度和租户混合负载，覆盖稳定流量、突发、持续高负载、冷启动、单租户集中提交和依赖故障；以计划的到达速率发起请求，避免只在上个请求结束后才发下一个而低估排队。报告被接受与被拒绝任务、正确完成率、首内容与完整耗时、积压恢复时间及成本。**本节交付物：** 容量模型、分层限额与调度策略、真实负载压测报告，以及明确的过载行为。

## 11. 长视频案例：分段并行提取，按证据逐层汇总

以一个两小时访谈为教学案例：用户希望尽快看到可回看的要点，最终获得完整章节、人物观点和时间戳。产品应分别提供“首段可用”和“整片完成”的目标，不能把快速返回一段开场摘要当成处理完长视频。这是对[视频下载与总结 Demo](/notes/ai-video-downloader-summarizer)的生产化设计延伸，不表示已有项目已经实现下述能力。

### 先选最省工作量的有效路径

先读取媒体元数据，核对时长、语言、可用字幕及访问权限。已有适用的带时间戳字幕时，优先解析与质量抽检；自动字幕可能缺字、错名或漏段，必要时仅补转缺失区间。需要转写时，优先获取音轨，不为纯语音总结下载和解码无用的高分辨率视频。

如果目标包括演示画面、图表、代码或无声动作，字幕不能代表全部内容；另做按场景或时间采样的关键帧、OCR 与视觉分析，并与音频时间轴对齐。向用户说明总结覆盖了语音还是视听内容，视觉采样也需要检查重要事件是否遗漏。

外部 ASR 可能支持整段音频的异步任务，也可以由应用分段调度。异步表示提交和取结果分离，不保证低延迟；对比供应商排队、上传、执行与取回时间后决定。Azure 的批量转写文档就采用提交任务、异步获取结果的模式。[Batch transcription](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/batch-transcription)

### 媒体分段与摘要分块分别设计

**媒体分段**服务于上传限制、转写吞吐和失败重试：结合语音活动检测（VAD）或静音位置，设置可调的最长片段、大小和少量上下文重叠，避免在半句话中间机械切断。分段长度取决于模型、语言、文件大小与硬件，不把固定五分钟当通则。视频无重编码切片还可能受关键帧影响；设置切片时间不等于得到绝对精确的边界。[FFmpeg：segment muxer](https://ffmpeg.org/ffmpeg-formats.html#segment)

每段保存 `segment_id`、原始起止时间、实际裁切起点、内容指纹、语言、版本与状态。把识别结果的局部时间加回实际源偏移；重叠区域按时间和文本对齐去重，保留跨段句子、术语与说话人线索。需要整片说话人一致性时另做对齐，不能假定各段的“speaker 1”都是同一人。

**摘要分块**服务于语义和上下文预算：在转写对齐后按话题、章节和 Token 预算重组，不必沿用音频切片。每块抽取事实、人物、观点与时间区间，再汇成章节，最后生成整片概览。汇总时保留证据引用并允许回查原文，避免只对越来越短的摘要继续摘要，丢掉关键反例与限定条件。

### 有界并行与逐步交付一起设计

分段就绪后即可派发有限数量的转写；已确认的段落可以继续抽取和显示，不必等所有片段结束。整片汇总要等待必需区间完成或明确标出缺失；乱序完成按原时间轴归并，取消后停止新增派发。普通 Worker 并行不是多个 Agent 自由协商，一条确定的任务流水线就能完成大部分工作。

重试只处理失败片段。用“授权范围 + 源内容指纹 + 阶段参数 + 模型 / 提示词版本”定义可复用产物；缓存读取仍要鉴权，并处理过期、删除和版本失效。恢复时复用已验证产物，对未知外部执行先查证。下载链接过期、字幕缺失、空白音频、异常时长、单段持续失败和后段卡住，都需要可查询的阶段状态与人工入口。

| 验证层 | 应保留的证据 | 发现问题后的动作 |
| :--- | :--- | :--- |
| 提取覆盖 | 预期媒体区间与成功片段区间、非静音缺口、失败和跳过原因 | 补转缺口；“已切分”不算“已转写”，静音单独标记 |
| 转写质量 | 语言、专有名词、数字、跨段句子与说话人的抽检 | 调整切分、术语或模型，并保留原转写版本 |
| 总结可信度 | 重要章节覆盖、关键结论的原文与时间戳、冲突和遗漏 | 回查原文，修正无依据结论；缺少后段时标记不完整 |
| 体验与效率 | 首个有证据的结果、整片耗时、音频处理实时因子、峰值资源、成本 | 定位下载、队列、ASR 或汇总瓶颈，比较改动前后 |

单独定义 `RTF = 转写计算耗时 / 对应音频时长`，数值越小表示该测量条件下计算越快；是否计入排队、上传和预处理须说明。整片用户耗时还包含这些阶段及后续汇总，不能用单段 RTF 代替。对比字幕直读、整片转写、分段转写和不同并发数时，保持输入与质量门槛一致。共享 GPU、限额、最长片段和汇总开销都可能限制提速，不能承诺“分成 N 段就快 N 倍”。

**本节交付物：** 阶段依赖与片段清单、可恢复产物、渐进结果协议，以及覆盖、质量、延迟和成本的对照报告。

## 12. 做到可观测、可承受、有人维护

### 从一个失败任务追到每个依赖

把接入、排队、检索、模型调用、工具执行、审批等待和结果保存连接到同一任务。记录输入输出的受控摘要或引用、耗时、Token、估算费用、版本、重试原因与错误分类。可参考 OpenTelemetry 的生成式 AI 语义约定统一遥测字段，并按采用版本核对具体字段。[GenAI semantic conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/)

调试 Trace 帮助理解发生了什么；审计记录帮助追责谁在何时批准和执行了什么，两者访问与保留策略可以不同。默认不采集完整敏感正文、密钥或模型内部推理；日志采样、脱敏和访问控制也属于系统设计。

监控应同时覆盖技术与业务：服务错误率、任务完成率、人工接管率、结果待核实任务数、越权拦截、重复副作用、队列积压、索引新鲜度和成本异常。P99 延迟突增时，先拆解是排队、检索、模型、工具还是审批等待；用户等待时间与自动执行耗时可分别统计。

### 用服务目标约束运行成本

服务水平指标 SLI 是实际测量值，服务目标 SLO 是承诺的目标范围。为不同任务定义统计窗口、分母和例外；例如只读问答的延迟目标与需要人工审批的任务不能混算。目标须与业务负责人协商并经压测验证。

成本建议以**每个成功任务的总成本**衡量，覆盖失败与重试、模型、检索、计算、存储和人工复核。模型费用可按输入、缓存输入、输出 Token 与供应商计费项估算，再与账单核对。

先优化上下文和重复调用，再评估缓存、批处理、较小模型路由及供应商切换。便宜模型增加重试后可能更贵；备用供应商也要通过质量、工具兼容和数据处理边界验证。缓存必须满足租户隔离、权限和失效规则。

将第 9–11 节的延迟、调度与分段指标连接到成本账：预算在并发派发前预留、完成后结算，避免多个 Worker 同时通过余额检查。费用告警要能追到租户、任务、片段和实际使用的版本。

### 运维不止看仪表盘

每个关键故障要有负责人、告警触发条件、操作手册与升级路径。演练 Worker 崩溃、数据库或供应商不可用、密钥轮换、备份恢复和队列重放。RPO 描述可接受的数据丢失窗口，RTO 描述恢复时间目标；有备份文件不代表已经验证恢复能力。

企业用户还需要组织成员与角色管理、SSO 与离职撤权、用量与账单、任务历史、审计导出、数据导出与删除，以及面向运维的重试、查证、补偿和人工接管入口。按客户要求逐步补齐，避免把全部能力挤进聊天窗口。

**本节交付物：** 仪表盘、SLO 与配额配置、告警及值守安排、恢复演练记录和管理员操作界面。

## 13. 贯穿案例：将知识问答 Demo 升级为服务平台

假设员工提交：“根据当前适用政策判断我的门禁问题怎么处理，必要时帮我创建服务工单。”可按下面的次序逐级增加能力。

| 阶段 | 增加的能力 | 通过标准 |
| :--- | :--- | :--- |
| 只读助手 | 身份与权限过滤、政策版本、引用与拒答 | 无权限资料不进入上下文；能回答、指出冲突或说明证据不足 |
| 工单草稿 | 提取需求、补问缺失信息、展示动作预览 | 申请人由服务端绑定；用户能确认位置、内容和提交范围 |
| 受控提交 | 审批、稳定操作 ID、幂等、状态查询 | 重复点击和重试后只产生同一业务操作；超时后先查证 |
| 团队试用 | 配额、Trace、反馈、任务恢复与人工入口 | Worker 重启后能继续；异常不会拖垮其他团队 |
| 平台运营 | 版本评估、灰度、审计、用量和恢复演练 | 能解释一次失败，停止不安全行为，并在目标时间内恢复服务 |

一次完整执行中，检索与工单创建可以保持固定流程；只有员工问题确实需要动态调查时才加入 Agent。假设创建工单的接口已经成功，但响应丢失，任务应显示“正在核实提交结果”，后台按操作 ID 查询。确认工单存在后保存外部 ID，再单独处理通知。通知失败不会让模型重新创建工单。

用户取消任务时，系统停止尚未开始的动作；已经发出的写请求仍需核实。若后来发现工单已创建，应向用户说明结果，并按业务规则提供关闭或人工处理入口。

这条路径可复用于内容生成、销售辅助、内部研究和数据分析产品：每增加一个外部动作，就补齐授权、状态、恢复和验证；每增加一层自主性，就证明其质量收益足以覆盖成本与风险。

## 14. 按风险分批交付，而不是一次搭完平台

| 批次 | 优先完成 | 进入下一批的条件 |
| :--- | :--- | :--- |
| A · 定义与基线 | 真实任务、传统方案对照、业务负责人、数据分级和初始评测 | 能明确衡量价值与错误影响 |
| B · 只读生产试点 | 身份与租户隔离、可靠检索、拒答、配额、观测与人工接管 | 有代表性任务上的质量与成本记录，关键隔离测试通过 |
| C · 开放写操作 | 工具鉴权、动作确认、幂等台账、超时查证、恢复与必要补偿 | 重复投递、崩溃、取消、未知结果等故障演练通过 |
| D · 扩大使用 | 回归门禁、灰度、流式恢复、混合负载容量与备份恢复、管理与审计能力 | 达到协商的服务目标，团队有能力持续维护 |
| E · 增加自主性 | 动态规划、模型路由或多 Agent 的对照实验 | 质量或业务收益超过额外复杂度与成本 |

批次是依赖顺序示例，不是固定工期。安全、评估和运维从第一批就开始，只是随风险加深。可以暂缓多 Agent，不能在已经开放写权限后再补幂等与鉴权。

上线前至少能够拿出以下证据：

- 有明确的业务成功标准、允许范围、负责人和人工接管路径。
- 跨租户访问、权限撤销、恶意资料和输出泄露的负向用例已验证。
- 任务有预算和终止条件，重复请求不会制造意外副作用。
- 超时未知结果、Worker 崩溃、取消与恢复均有可执行流程。
- 知识有来源和适用版本，证据不足或冲突时有明确行为。
- 发布版本能关联到评测结果，灰度和回退已演练。
- 受理、模型首 Token、用户首个有效内容和完整耗时分别有测量口径。
- 混合长度与租户负载压测通过，超限、断流、排队与取消有明确行为。
- 长媒体覆盖可核对，失败片段可重试，部分结果与整片完成清楚区分。
- 延迟、费用与容量目标有测量依据，超限后有降级策略。
- 告警有人接、备份能恢复，用户能查询状态并获得支持。

可以用下面的提示词审查自己的项目。审查应要求证据，未验证项应保留为未知，不能由 AI 自动宣布“已达到企业级”。

```prompt
你正在审查一个 AI 产品从 Demo 进入企业生产环境的准备情况。

项目资料：<PRD、架构、工具契约、数据流、评测与运行记录>
用户与租户：<使用者、角色、组织边界>
核心任务：<输入、结果、成功判定>
外部副作用：<工单、消息、支付或其他写操作>
目标与限制：<延迟、费用、数据处理与团队维护能力>
工作负载：<请求到达率、租户分布、输入时长与大小、供应商限额>

先阅读资料，区分已确认事实、目标和未知项，不假定项目必须使用 Agent 或多 Agent。

按业务适用性、执行状态、工具权限、重试幂等、故障恢复、
知识与记忆、租户隔离、评估发布、首内容与完整耗时、并发调度、
长任务分段、观测成本和运营支持进行审查。

每项输出：失效场景、影响、现有证据、缺口、最小改进、验证方法、负责人。
标出开放真实写权限前必须完成的项目，并给出按依赖排序的交付批次。
重点检查：外部成功但本地超时、重复投递、取消时仍有在途请求、
审批后参数或权限变化、检索到恶意内容、供应商不可用、配额耗尽。
对长任务另查：断流重连、慢客户端、队列积压、租户争抢、乱序分段、
缺失或重叠区间、字幕与视觉覆盖、部分结果与完整结果的区别。
分别要求受理、模型 TTFT、首个有效内容、整片耗时和成本的测量证据；
不能把异步、流式、分段或增加 Worker 直接视为已实现提速。

优先使用现有技术栈与简单方案。新增组件时说明必要性、替代方案及维护成本。
不要把提示词、框架能力或未经运行的测试计划当成已经实现的保证。
```

这一阶段完成后，交给下一轮迭代的应是一组可核查的成果：任务与权限契约、可恢复的执行记录、版本化评测、服务目标和运营手册。用实际任务与故障演练决定下一步投入，把自主性增加在已经验证能承担它的系统边界内。
